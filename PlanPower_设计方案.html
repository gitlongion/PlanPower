Windows 10 · 桌面软件设计方案

PlanPower — 定时电源管理器

一款面向 Windows 10 的轻量级计划任务工具：统一管理定时关机、重启、睡眠、休眠、锁定等电源动作。优先复用系统自带组件，不引入任何第三方运行库，单文件即可运行。

目标系统 Windows 10 1903+ / 11 推荐栈 C# + WPF + .NET Framework 4.8（系统内置） 零第三方依赖 双引擎调度

⚠ 本文档为 Revision 1，技术选型已被修订。因追加「免安装便携版 + 零依赖」需求，第 5.1 节的 C# + WPF + .NET Framework 4.8 方案不再适用——.NET Framework 属于 Windows 的可选功能，可被禁用，且在部分 Win10 版本上并未预装。

修订后的技术栈为 C++17 + Win32 API + 静态链接 CRT（/MT），实现真正的单文件零依赖。功能设计、界面设计、竞品调研、技术坑清单（第 1–4、6–8 章）仍然全部有效，请配合《PlanPower 便携版与零依赖专项设计》一并阅读。

1产品定位与设计原则

先说清楚这个软件「是什么」和「不做什么」。

一句话定位

把 Windows 自带任务计划程序的能力，包装成一个「看得懂、点得动、管得住」的电源任务管理中心。

四条硬约束

  • 只依赖系统自带组件。不打包 Python、不要求 .NET 8/9/10 运行时、不引 NuGet 包。用户双击即用，卸载就是删文件。
  • 任务必须能跨重启存活。这是和绝大多数「倒计时关机小工具」最本质的区别——软件没开、电脑重启过、甚至处于休眠状态，任务照样生效。
  • UI 一眼看懂。主界面只回答三个问题：有哪些任务？下次什么时候跑？现在是开还是关？
  • 危险操作必须可逆。任何会导致关机的动作，都要有提前提醒和一键取消。

不做什么（划清边界）

  • 不做通用自动化平台（那是 zTasker 的地盘），只聚焦电源与系统状态类动作。
  • 不做远程批量管理控制台（可选留一个 shutdown /m 的扩展点即可）。
  • 不联网、不上报、不自动更新——降低杀软误报和隐私顾虑。

调研结论：这个赛道上的开源项目分成两派——一派是「轻量倒计时器」（ShutdownTimerClassic、ShutdownTool），体验好但任务不持久、不能重复；另一派是「系统计划任务的前端」（FluentTaskScheduler、WinShutdownTool 的「生成系统计划」），能持久但交互原始。

PlanPower 的机会点，就是把这两派合起来：用系统计划任务做持久化的底座，用现代 UI 做交互层，并补齐两者都缺的「多任务并行管理 + 条件触发 + 唤醒执行」。

3可额外增加的功能建议

26 项，按「核心必备 / 高价值低成本 / 差异化进阶 / 锦上添花」四档排列。每项都标注了用途与价值。

A. 核心必备（第一版就该有）

A1 · 提前提醒 + 一键取消窗口必备

用途：任务执行前 N 秒（可配置，默认 60 秒）弹出置顶窗口，显示倒计时、「立即执行」和「取消本次」两个按钮。

价值：这是防数据丢失的第一道闸门。同类软件里 ShutdownTimerClassic 用「强制/优雅」二分法规避风险，WinShutdownTool 用 55 秒弹窗，本质都是同一诉求。配合 shutdown /a 实现零成本取消。

A2 · 任务持久化到系统计划任务必备

用途：创建的长期/重复任务写入 Windows 任务计划程序的独立文件夹，软件关闭后仍生效。

价值：解决「软件一关任务就没了」这个最大痛点，也让程序本体可以完全退出、不占内存、不需要开机自启。

A3 · 唤醒执行（Wake To Run）必备同类少见

用途：允许任务在电脑处于睡眠 / 休眠状态时，通过主板 RTC 定时唤醒并执行。

价值：任务计划程序的原生能力（<WakeToRun>），但绝大多数同类软件都没有暴露出来。这让「凌晨 3 点自动唤醒开机跑备份再关机」成为可能。软件内用 powercfg /waketimers 展示当前已注册的唤醒定时器，让用户能确认硬件是否真的会醒。

A4 · 错过补跑（Start When Available）必备

用途：如果计划时间点电脑恰好关机或休眠未唤醒，开机后自动补执行。

价值：笔记本合盖、临时断电等场景下的兜底。默认开启，可在任务高级设置中关闭。

A5 · 多任务并行列表必备

用途：主界面以列表呈现全部任务，每行显示动作类型、计划规则、下次执行时间、启用状态。

价值：这是与「单倒计时小工具」拉开差距的地方。用户可以同时挂「每天 23:00 关机」「工作日 08:30 唤醒」「30 分钟后睡眠」三条互不干扰的规则。

B. 高价值低成本（强烈建议）

B1 · 空闲触发关机建议

用途：当系统持续空闲（无键鼠输入、CPU 低负载）超过 N 分钟后执行关机或睡眠。

价值：下载、渲染、编译这类「不知道还要多久」的场景，不用猜时间。zTasker 靠这个功能吸引了大量用户。实现上可直接用任务计划程序的 ONIDLE 触发器，零额外成本。

B2 · 指定进程退出后关机建议差异化

用途：监听某个进程（如游戏、视频转码器、编译任务），一旦它退出，延迟 N 秒后执行电源动作。

价值：「下完就关」「渲染完就关」的精确版本，比空闲检测更准确。可用 WMI 事件订阅 Win32_ProcessStopTrace 实现，不需要轮询。

B3 · 倒计时悬浮窗建议

用途：存在进行中的倒计时任务时，显示一个半透明、可拖拽、置顶的小窗口，实时显示剩余时间。

价值：降低「忘记有任务在跑」导致的意外关机。ShutdownTimerClassic 用整窗变色来实现类似效果，悬浮窗对主界面干扰更小。

B4 · 强制关闭 / 优雅关闭 双模式建议

用途：每个任务可选是否加 /f 强制参数。优雅模式让应用自己退出（可能有程序弹窗阻止关机），强制模式直接结束进程。

价值：ShutdownTimerClassic 的核心设计之一。默认优雅，把「可能失败」和「可能丢数据」的选择权交给用户。

B5 · 电池感知建议

用途：任务可配置为「仅接通电源时执行」，或「电量低于 X% 时执行关机」。

价值：任务计划程序的 DisallowStartIfOnBatteries 默认值会静默吞掉任务，很多用户被这个默认值坑过。把它变成显式选项，并额外提供低电量自动关机——这是笔记本用户真正需要的。

B6 · 关机前收尾动作建议差异化

用途：关机前依次执行可选的收尾动作：结束指定进程、断开 VPN / 网络映射盘、静音、清空回收站、锁定 BitLocker 卷、执行一段自定义脚本。

价值：让「关机」从单一动作升级为一条工作流。尤其是「断开 VPN 再关机」，能避免公司网络策略导致的关机阻塞。

B7 · 任务模板与一键预设建议

用途：内置常用预设：「下班关机（工作日 18:30）」「睡前休眠（每天 23:30）」「下载完关机（空闲 20 分钟）」「午休锁定（每天 12:00）」。

价值：把上手成本从「填表单」降到「点一下」。这是新用户留存的关键，也是同类软件普遍缺失的一环。

B8 · 托盘常驻与快捷菜单建议

用途：最小化到系统托盘；右键菜单提供「30 / 60 / 120 分钟后关机」「取消当前倒计时」「打开主界面」。

价值：高频操作零层级直达。Chronoff、ShutdownTool 都做了托盘，属于事实标准。

B9 · 执行日志与历史建议

用途：记录每次任务的计划时间、实际执行时间、结果（成功 / 被取消 / 被阻止）、触发来源。

价值：出问题时能定位（是任务没触发，还是触发了但被程序阻止）。数据源可直接读任务计划程序的 LastRunTime / LastTaskResult，再叠加本地的取消记录。

B10 · 导入 / 导出配置建议

用途：把全部任务导出为单个 JSON 文件，可导入到另一台机器。

价值：换机迁移、给同事分发统一规则、备份。成本极低（序列化一个列表），收益明确。

C. 差异化进阶（让产品有记忆点）

C1 · 全局热键触发进阶

用途：给任意任务绑定全局快捷键，按下即执行。

价值：zTasker 的招牌能力之一。对 PlanPower 而言，一个「Ctrl+Alt+S 立即睡眠」就足够有说服力。用 RegisterHotKey 实现，无额外依赖。

C2 · 命令行接口进阶

用途：支持 PlanPower.exe /shutdown 30 /message "要关机了" 这类静默参数，执行后立即退出，不显示界面。

价值：可被批处理、快捷方式、其他软件调用，等于免费获得一个扩展生态。对开发者用户群尤其有吸引力。

C3 · 关机前二次确认 / 密码保护进阶

用途：可选设置密码，取消或修改进行中的任务必须输入密码。

价值：Chronoff 的差异化功能。适用于家长控制（防止孩子取消定时关机）、公共机房、共享电脑。注意：这不是安全边界，只是防误操作。

C4 · 随机延迟进阶

用途：计划时间附加 ±N 分钟随机抖动，例如「23:00 ± 10 分钟」。

价值：机房、办公室批量部署时，避免几十台机器同时关机造成瞬时负载冲击。实现成本几乎为零（在生成触发器时加随机偏移）。

C5 · 局域网批量控制进阶

用途：对同一网段内的其他 Windows 机器下发关机 / 重启指令。

价值：基于系统自带的 shutdown /m \\计算机名，无需装客户端。适合小型办公网络、家庭多机。门槛在于目标机的凭据与防火墙配置，需要清晰的引导文案。

C6 · 看门狗：有未保存工作则跳过进阶

用途：执行前检查是否存在指定的「保护进程」（如 Word、Photoshop、IDE），若存在则跳过本次并记录日志，或延后 N 分钟重试。

价值：把「强制关机」的风险降到最低。这是纯粹的体验加分项，能显著减少用户投诉。

C7 · 网络条件触发进阶

用途：「下载完成后（网速低于阈值持续 N 分钟）关机」或「断网超过 N 分钟后关机」。

价值：比空闲检测更贴合下载场景。需要读取网卡计数器（PDH 性能计数器，系统自带），有一定实现成本，放在后期。

C8 · 屏幕/显示器节能动作进阶

用途：除关机外，支持「关闭显示器」「启动屏保」「锁定工作站」三个轻量动作。

价值：不是所有场景都需要关机。短暂离开时关显示器比关机更合适。实现只需一条窗口消息广播，成本极低。

D. 锦上添花（有余力再做）

D1 · 深色模式与主题色可选

用途与价值：跟随系统深浅色，提供 2–3 种强调色。Chronoff 做了这件事且用户评价不错。WPF 下通过资源字典切换即可。

D2 · 多语言界面可选

用途与价值：中文 + 英文双语文案，用 .resx 资源文件管理，系统自带能力，无额外依赖。

D3 · 高 DPI 与多显示器适配可选

用途与价值：在 125% / 150% 缩放下不模糊、悬浮窗落在正确的显示器上。属于「不做会被骂」的基础质量项。

D4 · 任务执行前语音/音效提示可选

用途与价值：提醒窗口弹出时播放系统提示音，或在最后 10 秒用语音倒计时。增强临场感，对「在隔壁房间」的场景有用。

D5 · 便携模式可选

用途与价值：检测到同目录存在 portable.flag 时，配置写入程序目录而非 %AppData%，可直接放 U 盘使用。

+ .NET Framework 4.8		 系统内置 约 150 – 500 KB 中，控件老旧需自绘 低 启动最快、代码最简；UI 现代感不足。适合「极简优先」的取舍
C++ / Win32
+ COM		 无 约 150 – 300 KB 弱，需手写控件或引入资源 高 体积与依赖的极致，但 UI 开发代价过大
C# + .NET 8/9/10
（自包含 AOT）		 无（自包含） 约 10 – 15 MB 强 中 体积换独立性。Chronoff 走的是这条路（.NET 10 + WPF）
PowerShell + WinForms 系统内置 脚本文件 中 低 无需编译，但启动慢、有控制台闪窗、易被杀软误报，不适合作为正式产品

选型结论：主方案 C# + WPF + .NET Framework 4.8。理由有三：

① .NET Framework 4.8 是 Windows 10 1903 及以后版本的系统组件，不需要用户安装任何东西，严格满足「无第三方运行库依赖」；

② WPF 的 XAML 数据绑定 + 样式模板，是做「卡片列表 + 向导式表单 + 悬浮窗」这类现代 UI 的最短路径；

③ 编译产物是纯托管程序集，单文件 exe 通常 < 1 MB，远小于 .NET 8 自包含方案的 10 MB+。

如果后续对体积或启动速度有极致要求，可以降级到 WinForms 重写界面层——业务层代码完全不用改，这也是下面分层设计的价值所在。

5.2 双引擎调度架构（核心设计）

这是本方案与同类软件最重要的区别。任务按性质分派给两个引擎，但用户在界面上看到的是一份统一列表。

任务特征走哪个引擎原因
「30 分钟后关机」（倒计时）TimerEngine无需提权、可随时暂停改时间，反馈即时
「今天 22:00 关机」（一次性）TimerEngine
（可升级为 B）		时间近，常驻内存成本可忽略
「每天 23:00 关机」（重复）SchedulerEngine必须跨重启存活
「工作日 08:30 唤醒开机」SchedulerEngine需要 WakeToRun，且此时软件未运行
「空闲 20 分钟后关机」SchedulerEngine直接用系统 ONIDLE 触发器

为什么不做成「全部走系统计划任务」？因为创建系统级任务需要管理员权限，而「我就想 30 分钟后关个机」这种高频轻量场景不值得每次都弹 UAC。双引擎的本质是按需提权：轻量任务完全不碰系统，只有需要持久化时才触发一次提权。

5.4 与任务计划程序集成：三条路径，按需选择

路径一（首选）：COM ITaskService

任务计划程序的官方编程接口，返回结构化对象，不受系统语言影响。C# 中通过 COM 互操作调用——注意这里不需要引 NuGet 包（网上流传的 Microsoft.Win32.TaskScheduler 是第三方库，本方案不用它），而是手写 COM 接口声明或使用 Type.GetTypeFromProgID + dynamic。

// 连接任务计划程序服务（COM ProgID: Schedule.Service）
var type = Type.GetTypeFromProgID("Schedule.Service");
dynamic svc = Activator.CreateInstance(type);
svc.Connect();

// 打开我们自己的任务文件夹（不存在则创建）
dynamic root = svc.GetFolder("\\");
dynamic folder;
try { folder = svc.GetFolder("\\PlanPower"); }
catch { folder = root.CreateFolder("PlanPower"); }

// 枚举全部任务
foreach (dynamic t in folder.GetTasks(1))   // 1 = TASK_ENUM_HIDDEN
{
    Console.WriteLine($"{t.Name}  下次执行: {t.NextRunTime}  状态: {t.State}");
}

路径二（备用）：schtasks.exe + XML 模板

当 COM 调用因环境问题失败时降级使用。做法是先生成任务 XML 写入临时文件，再执行 schtasks /create /xml。

两个必须注意的坑：① schtasks /create /xml 要求 XML 文件为 UTF-16 LE 带 BOM 编码，用 UTF-8 会直接报错；② 路径含中文或空格时，/tn 参数必须完整加引号。

<?xml version="1.0" encoding="UTF-16"?>
<Task version="1.2" xmlns="http://schemas.microsoft.com/windows/2004/02/mit/task">
  <RegistrationInfo>
    <Description>PlanPower 任务：工作日 23:00 关机</Description>
    <Author>PlanPower</Author>
  </RegistrationInfo>

  <Triggers>
    <CalendarTrigger>
      <StartBoundary>2026-10-12T23:00:00</StartBoundary>
      <Enabled>true</Enabled>
      <ScheduleByWeek>
        <WeeksInterval>1</WeeksInterval>
        <DaysOfWeek><Monday/><Tuesday/><Wednesday/><Thursday/><Friday/></DaysOfWeek>
      </ScheduleByWeek>
    </CalendarTrigger>
  </Triggers>

  <!-- S-1-5-18 = LOCAL SYSTEM：无人登录也能执行 -->
  <Principals>
    <Principal id="Author">
      <UserId>S-1-5-18</UserId>
      <RunLevel>HighestAvailable</RunLevel>
    </Principal>
  </Principals>

  <Settings>
    <MultipleInstancesPolicy>IgnoreNew</MultipleInstancesPolicy>
    <!-- 关键：默认值 true 会让笔记本在电池下静默不执行 -->
    <DisallowStartIfOnBatteries>false</DisallowStartIfOnBatteries>
    <StopIfGoingOnBatteries>false</StopIfGoingOnBatteries>
    <!-- 错过后开机补跑 -->
    <StartWhenAvailable>true</StartWhenAvailable>
    <!-- 允许唤醒处于睡眠/休眠的电脑 -->
    <WakeToRun>true</WakeToRun>
    <ExecutionTimeLimit>PT5M</ExecutionTimeLimit>
    <Enabled>true</Enabled>
  </Settings>

  <Actions Context="Author">
    <Exec>
      <Command>shutdown.exe</Command>
      <Arguments>/s /t 60 /c "系统将在 60 秒后关机"</Arguments>
    </Exec>
  </Actions>
</Task>

路径三（兜底）：直接操作 Tasks 目录 + 注册表

任务计划程序把每个任务以 XML 文件存放在 %SystemRoot%\System32\Tasks\ 下，运行时启用状态则在 HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Schedule\TaskCache\Tree\。仅在 COM 与 CLI 双双不可用时作为最后的诊断手段，不建议作为常规实现路径。

为什么不用 schtasks /query /fo csv /v 做数据源？因为它的输出表头会随系统语言变化——中文系统上是「任务名 / 下次运行时间」，英文系统上是 "TaskName / Next Run Time"。靠解析这个文本来枚举任务，换台机器就崩。枚举一律走 COM 或 /xml。

5.5 权限与提权模型

这是决定用户体验好坏的关键设计。三种方案对比：

方案体验问题取舍
清单声明 requireAdministrator 每次启动弹 UAC 拖拽文件失效、托盘与资源管理器交互受限；日常查看任务也要提权，很烦 简单但不优雅
清单声明 asInvoker，全程不提权 最清爽 无法创建 SYSTEM 权限的计划任务，引擎 B 直接不可用 功能残缺
asInvoker + 按需提权辅助进程 日常零打扰 需多写一个辅助进程入口与 IPC 推荐

推荐方案的流程：主程序以普通权限运行 → 用户点击「保存任务」且该任务需要写入系统计划任务时 → 主程序用 ShellExecute 加 runas 动词拉起自身（带 /elevated-write 参数）→ 提权实例执行 schtasks 命令 → 返回结果 → 主程序刷新列表。整个过程只弹一次 UAC。

// 主程序：按需提权
var psi = new ProcessStartInfo
{
    FileName        = Application.ExecutablePath,
    Arguments       = "/elevated-write \"" + taskXmlTempFile + "\"",
    Verb            = "runas",          // 触发 UAC
    UseShellExecute = true
};
try { Process.Start(psi)?.WaitForExit(); }
catch (Win32Exception) { /* 用户点了「否」，友好提示并保留草稿 */ }

5.6 数据模型与存储

权威数据源是系统任务计划程序（引擎 B 的任务）与本地 JSON（引擎 A 的任务 + 全部 UI 扩展元数据）。两者用任务名中的 GUID 后缀做映射。

class PowerTask
{
    public Guid      Id            { get; set; }
    public string    Name          { get; set; }   // 用户可见名称
    public PowerAction Action      { get; set; }   // Shutdown/Restart/Sleep/...
    public ScheduleKind Kind       { get; set; }   // Countdown/Once/Daily/Weekly/...
    public TriggerSpec  Trigger    { get; set; }   // 时间参数（多态）

    // ---- UI 扩展元数据（系统任务里存不下，存在本地 JSON）----
    public int       NoticeSeconds { get; set; }   // 提前提醒秒数，默认 60
    public bool      ForceClose    { get; set; }   // 是否加 /f
    public string    Message       { get; set; }   // 关机提示文本
    public bool      WakeToRun     { get; set; }
    public bool      RunOnlyOnAC   { get; set; }
    public bool      Enabled       { get; set; }
    public List<string> PreActions  { get; set; }   // 收尾动作

    // ---- 运行时状态（从系统查询，不持久化）----
    public DateTime? LastRunTime   { get; set; }
    public DateTime? NextRunTime   { get; set; }
    public int       LastResult    { get; set; }
    public Engine    Owner         { get; set; }   // Timer / TaskScheduler
}

存储位置：

  • 配置与元数据：%AppData%\PlanPower\tasks.json（便携模式下改为程序目录）
  • 序列化：用 .NET 内置的 DataContractJsonSerializer 或 JavaScriptSerializer，不引 Newtonsoft.Json
  • 系统任务命名规范：\PlanPower\{用户名称}_{Id 前 8 位}，便于枚举时精确过滤、避免污染用户已有任务

5.8 关键流程：创建一条「工作日 23:00 关机」

  1. 用户在向导里选「关机」→「每周」→ 勾选周一至周五 → 时间 23:00 → 提前提醒 60 秒 → 强制关闭程序（否）。
  2. 向导底部实时生成自然语言预览：「每个工作日 23:00 关闭计算机，提前 60 秒提醒，等待程序自行退出。」
  3. 点击保存 → TaskOrchestrator 判定为「重复任务」→ 路由到 SchedulerEngine。
  4. 生成任务 XML 到临时文件 → 提权实例执行 schtasks /create /tn "\PlanPower\工作日关机_a1b2c3d4" /xml "temp.xml" /f。
  5. 写入成功 → 把 UI 元数据写入本地 tasks.json → 刷新列表，显示「下次执行：今天 23:00」。
  6. 到点前 60 秒，若主程序在运行则弹出提醒窗；用户点「取消本次」→ 执行 shutdown /a 并记录日志；未操作则系统按计划执行关机。

细节设计：任务执行前 60 秒的提醒由谁负责？如果主程序没运行，就没有提醒窗——这是「可持久化」的代价。折中方案是在任务 XML 里把实际命令写成两段：shutdown /s /t 60 /c "..."，让 Windows 自己在系统层弹出倒计时提示，用户仍可用 shutdown /a 取消。这样即使 PlanPower 完全没运行，用户也有 60 秒反悔窗口。

6.2 新建任务向导（三步）

第 1 步 · 做什么

6.3 交互细节约定

  • 启用开关是行内的，点击立即生效，不需要进详情页——这是最高频的操作。
  • 删除必须二次确认，确认框里直接显示任务的自然语言描述，避免误删。
  • 倒计时任务在列表中高亮并显示实时剩余时间（每秒刷新，用 DispatcherTimer）。
  • 危险动作有颜色区分：关机 / 重启用暖色标识，锁定 / 关屏用中性色，视觉上区分「会丢数据」和「不会」。
  • 空状态有引导：没有任务时显示模板卡片（「下班关机」「下载完关机」），点击即创建。
  • 状态栏常驻显示权限状态：让用户知道当前是「标准用户」还是「已提权」，出问题时能自助判断。

7已知风险与技术坑

这些是实际开发时一定会撞上的问题，提前列出比事后 debug 便宜得多。

#问题影响应对
1 睡眠变成休眠：SetSuspendState(false, false, false) 在系统已启用休眠时，实际执行的是休眠而非睡眠 用户以为电脑会秒醒，结果半小时才启动 优先使用 NtSetSystemPowerState（PowerActionSleep）；或调用前用 powercfg /a 检测，若休眠已启用则明确提示用户「当前将执行休眠」，并在设置里提供一键 powercfg /h off 的说明
2 现代待机（Modern Standby / S0）机型行为不同 powercfg /a 显示 S0，不支持传统 S3 睡眠，唤醒定时器行为不一致 启动时检测，若为 S0 机型则隐藏「唤醒执行」选项并给出说明，避免用户配了却无效
3 快速启动导致的混合关机：Win10 默认开启快速启动，「关机」实际是混合关机，不完全断电 某些场景（换硬件、进 BIOS）行为不符预期 在高级设置中提供「使用完全关机（/full 或先 powercfg /h off）」选项并解释差异
4 计划任务在电池供电时被静默跳过 笔记本用户配了任务却完全不执行，且没有任何报错 生成 XML 时显式写入 <DisallowStartIfOnBatteries>false</DisallowStartIfOnBatteries>，并在 UI 上把「仅接通电源时运行」做成可见选项而非隐藏默认值
5 XML 编码问题：schtasks /create /xml 要求 UTF-16 LE + BOM 用默认 UTF-8 写入会直接创建失败，报错信息还很含糊 统一用 new UnicodeEncoding(false, true) 写临时文件；或干脆走 COM 路径绕开
6 schtasks /query /fo csv /v 表头随系统语言变化 用文本解析做数据源，换语言环境直接崩 枚举一律走 COM ITaskService 或 /query /xml，绝不解析本地化文本
7 shutdown /t 上限 315360000 秒（10 年），超出直接报错 用户输入超长时间时崩溃或静默失败 输入层做范围校验并给出明确提示；超长任务改用计划任务而非 /t
8 shutdown /s 不保存未保存的文档 数据丢失，是最严重的用户投诉来源 默认开启提前提醒；提供「优雅关闭」模式；可选看门狗检测指定进程存在时跳过
9 系统时间被手动修改 / 时区变更 倒计时错乱或提前触发 倒计时用单调时钟（Environment.TickCount64）而非墙钟；绝对时刻任务交给系统计划任务处理
10 msg.exe 在 Win10 家庭版不存在 用命令行弹提示的方案在家庭版失效 提示一律用自绘 WPF 窗口，不依赖 msg
11 组策略禁用 shutdown.exe（企业环境常见） 所有关机功能失效 降级到 P/Invoke：InitiateSystemShutdownEx 或 ExitWindowsEx(EWX_SHUTDOWN \| EWX_FORCE)，启动时探测并自动选择可用通道
12 杀软启发式拦截：单文件 exe 频繁调用 shutdown.exe 容易被判定为可疑行为 误报、隔离、用户不敢用 程序不联网、不写系统目录、不上报；提供数字签名（若有条件）；在 README 中说明行为，减少用户疑虑
13 UAC 被用户拒绝 任务保存失败但草稿丢失，用户白填一遍表单 提权失败时保留草稿并友好提示，提供「以内存计时方式临时执行」的降级选项
14 任务被用户手动在系统计划程序里改坏 软件读取到非预期状态 读取时做健壮性校验，无法解析的任务在列表中标记为「外部修改」并允许一键修复或清理
