专项设计 · 便携版关键矛盾拆解

系统级持久任务：显式可选 + 可一键清理

「任务要能跨重启存活」与「程序不留痕」是便携软件绕不开的一对矛盾。这份文档把这对矛盾的解法完整拆开：默认不持久、开启需显式同意、写入可完整回收、并且随时能看到自己在这台机器上留了什么。

默认关闭 显式同意后启用 三级清理入口 归属机器识别 孤儿任务检测

本设计解决的问题：PlanPower 是便携软件，运行在别人的机器上、跑在 U 盘里。但「每天 23:00 关机」这类需求天生要求任务能跨重启存活——而唯一可靠的实现方式是写入 Windows 任务计划程序，这会在宿主机器上留下痕迹。

如果不管：U 盘拔走后，那台机器上还挂着一堆不知道从哪来的关机任务，用户无法解释也无法清理，这是不可接受的。如果一刀切禁用：产品就退化成普通倒计时小工具，丢掉最核心的差异化。

所以答案是第三条路：把它做成一个需要显式同意、且可完整回收的可选能力。

实现状态（v0.2.2）：已按本文落地。三道闸门、三级清理、归属识别、动作兼容性矩阵、提权助手与命令行应急清理均已写进代码并通过离线验证。

落地时补充的一条约束：系统持久任务不进入内存计时器——它的执行者是 Windows，本程序不参与计时。早期实现两边都排，结果内存这条到点用 timeout=0 立刻执行，把 shutdown.exe /t N 争来的宽限窗口当场掐掉，提醒窗上的「取消本次」也变成谎话（取消了内存这条，系统那条照样执行）。现在改为：系统任务由任务计划程序全权负责，界面用它推算出的「下次执行」时刻来展示，只当计划看，不当进度看。

另一条落地时收紧的口径：失败路径做成原子的。降级（系统 → 内存）时先摘系统任务再写盘，摘不掉就整体中止保存；删除系统任务失败时不删本地记录。否则会留下一条界面上看不见、后台却照常执行的任务——用户连从哪儿关掉都找不到。

v0.2.2 补的一条：注册本身也要有退路。真机上服务端以 SCHED_E_INVALIDVALUE（0x80041318，「任务 XML 包含一个格式不正确或超出范围的值」）整段拒绝了任务定义。这个错误名下的约束有一部分文档里没写、只能实测，无法在开发机上复现。于是把定义拆成完整版与精简版两套，按「定义风格 × 版本 × 身份写法」的顺序降级重试（详见 README 的 v0.2.2 修复记录）。关键约束是降级不许改坏行为：精简版可以省掉与默认值等价的冗余项，但「不因电池而跳过」「错过补跑」「唤醒执行」「启停状态」「执行时限」这五项必须两套都有——把用户从「注册失败」换成「注册成一条行为不对的任务」，比直接失败更糟。

v0.2.1 修复：真机反馈「选择系统持久任务时，保存提示『注册系统任务失败』」。

主因不在任务计划程序，而在配置文件的写入方式。当时用 kernel32 的 WritePrivateProfileString 存配置——它写的是进程内缓存，延迟落盘，全程没有 flush。而「注册系统任务」这一步是父进程保存完立刻 ShellExecuteEx(runas) 拉起提权助手去做的，助手从磁盘读 INI，读到的要么是旧内容、要么文件还不存在，于是按任务 ID 查不到任务。偏偏 SchedDoAdd 的所有失败分支共用同一个标题，「找不到任务」被伪装成了「注册系统任务失败」。

次因：RegistrationInfo 里手写的 <URI>\PlanPower\xxx</URI>。任务路径本来就由 RegisterTaskDefinition 的第一个参数决定、服务端自己推导；手写一个以反斜杠开头的 URI，一旦与注册路径有任何出入就以 0x80041318（XML 取值非法）被整段拒绝，而报错完全指不到这个元素上。已删除。

修法：① 配置读写改为自己实现——整段拼好后写临时文件 → FlushFileBuffers → MoveFileExW 原子替换，彻底弃用 Profile API；② 注册拆成 put_XmlText（只验 XML 合法性）与 RegisterTaskDefinition（验权限 / 路径 / 身份）两步，两阶段失败文案不同；③ 错误说明改为「十六进制错误码 + FormatMessageW 取系统自带中文说明」，不再硬编码错误码表；④ 「找不到任务」时一并报出配置文件路径与读到的任务条数。

顺带发现：给宿主测试加 -I src 会让 libc++ 内部的 #include <sched.h> 命中项目里的 src/sched.h，把 core.h → <vector> 拖进一个正在展开的 <vector>，报出一堆莫名的 no member named 'min'。改用 -iquote src（只作用于引号形式的包含）。

回归防护：新增 tools/initest.cpp（112 项 INI 往返断言）与 tools/check_layout.py 的 E 组跨文件不变量（14 条，锁住上述每一条修法）。11 类手工注入的回归全部被准确捕获。

1设计原则

四条原则决定了后面所有的具体设计。

① 默认不持久

便携是主场景，持久是可选增强。新装即用状态下，程序一个字节都不往宿主机写。用户不主动开启，就永远不会产生残留。

② 显式同意

开启时必须说清楚三件事：会写什么、写在哪、怎么清理。用户勾选确认后才生效。不做静默升级，不做「默认帮你勾上」。

③ 可逆

任何写入都必须有对应的删除路径，且删除路径不依赖原配置文件——即使 INI 丢了、U 盘换了，也必须能清干净。

④ 可发现

用户随时能看到「我在这台机器上留了什么」。状态栏常驻显示已注册的系统任务数量，一键直达清理入口。

2任务状态模型

要管好这些任务，先得把「任务可能处于哪些状态」定义清楚。

2.1 两个正交维度

每个任务由两个维度共同描述：

  • 引擎维度：由谁执行 —— 内存 内存计时器（PlanPower 自己执行）／ 系统 任务计划程序（由 Windows 执行）
  • 归属维度：这条记录属于哪台机器 —— 本机／其他机器（配置随 U 盘带过来的）

2.2 完整状态表

引擎系统里实际存在？归属界面显示用户可做的操作

系统 是，且内容匹配 本机 正常显示，标注「系统任务 · 已注册于本机」 全部操作

「孤儿任务」是最需要处理好的情况。它指的是：\PlanPower 文件夹里存在某个计划任务，但当前配置文件里没有对应记录。产生原因通常是——用户把 INI 删了、换了台机器、或者上一次注册后 U 盘丢失。这些任务必须能被发现和清理，否则就成了永久残留。

3交互设计：三道闸门

从「默认不持久」到「真的写入系统」，用户需要主动跨过三道门槛。每一道都让代价更清楚。

第一道闸门 · 全局能力开关

位于设置页，名为「允许创建系统级持久任务」，默认关闭。首次开启时弹出说明对话框：

启用系统级持久任务？
开启后，你可以把任务注册到本机的 Windows 任务计划程序中。这样做的好处是：
  • 即使 PlanPower 未运行，任务依然会按时执行
  • 即使电脑重启过，任务依然有效
  • 任务可以唤醒处于睡眠或休眠状态的电脑
需要了解的代价：
  • 会在本机任务计划程序的 \PlanPower 文件夹下留下记录
  • 需要管理员权限（每次注册会弹出 UAC 确认）
  • 离开这台电脑前，请使用「清理全部系统任务」
✓我已了解，并会在离开本机前清理

「启用」按钮在勾选确认前为禁用状态，不可跳过。

第二道闸门 · 任务级选择

创建向导第 3 步新增「任务类型」选项组，默认选中「内存计时」：

⚡ 内存计时　默认

立即生效，不需要管理员权限，退出 PlanPower 后失效。

适合：临时的「30 分钟后关机」「今天 22:00 重启」

📌 系统持久任务

跨重启存活，可唤醒睡眠中的电脑，需要管理员权限，会在本机留下记录。

适合：长期的「每个工作日 23:00 关机」「每天 08:30 唤醒开机」

选择「系统持久任务」后，向导底部的预览条追加一行提示：

「将在本机注册一个系统任务，需要管理员权限。离开本机前记得清理。」

第三道闸门 · 每次写入前的 UAC

每次实际写入系统时（创建、修改、删除、启停系统任务），由 Windows 弹出 UAC 确认。这既是系统要求，也是一次自然的「你确定吗」。

为什么不做「一次提权，全程免打扰」？因为那意味着程序长期持有管理员权限，一旦有漏洞影响面更大；而且每次操作都有 UAC 确认，用户对「我正在往系统里写东西」这件事始终有感知。对于一个宣称「便携不留痕」的软件，这种透明性比便利性更重要。

4归属识别：知道任务是谁留下的

U 盘会插到很多台机器上。配置跟着盘走，但系统任务留在各台机器里。必须能区分「这条任务是在本机注册的」还是「在别的机器上注册的」。

4.1 机器指纹

在不写注册表的前提下，用两个稳定标识组合出机器指纹：

// 取计算机名 + 系统盘卷序列号，哈希后取 8 位十六进制
wchar_t computerName[MAX_COMPUTERNAME_LENGTH + 1];
DWORD size = MAX_COMPUTERNAME_LENGTH + 1;
GetComputerNameW(computerName, &size);

wchar_t sysRoot[MAX_PATH];
GetWindowsDirectoryW(sysRoot, MAX_PATH);
sysRoot[3] = L'\0';                 // "C:\"

DWORD volumeSerial = 0;
GetVolumeInformationW(sysRoot, nullptr, 0, &volumeSerial,
                      nullptr, nullptr, nullptr, 0);

// 组合 + 哈希（自实现的 FNV-1a，约 10 行）→ 例如 "7F3A9C21"

4.2 归属记录（写在 INI 里，随 U 盘走）

; PlanPower.ini —— 记录"我在这台机器上留了什么"
[Host.7F3A9C21]
name=DESKTOP-ABC
lastseen=2026-10-12T21:15:00
tasks=\PlanPower\工作日下班关机_a1b2c3d4,\PlanPower\早晨唤醒_e5f6a7b8

[Host.2B8E4D10]
name=LAPTOP-XYZ
lastseen=2026-10-05T09:30:00
tasks=\PlanPower\临时关机_c9d0e1f2

启动时，程序用当前机器的指纹去查这个表：

  • 命中 → 这些系统任务属于本机，正常显示、可编辑、可清理
  • 未命中但表里有其他机器 → 那些任务显示为「注册于 DESKTOP-ABC」，本机不可编辑，只提供「在本机重新注册」
  • 本机指纹不在表里，但系统里发现了 \PlanPower 任务 → 判定为孤儿，提示清理

这个表可能失效。如果用户删了 INI、或者 U 盘丢了，归属信息就没了。所以归属表只是「优化项」，真正的兜底是任务名里的 PlanPower 前缀和 \PlanPower 文件夹——只要看到这个文件夹，就知道是本程序留下的，可以清。这也正是下一节「应急清理入口」存在的理由。

5三级清理入口

按「粒度从细到粗、依赖从多到少」排列。最关键的是第三级——它不依赖任何本地数据。

第一级 · 任务级

删除单个系统任务时，同步删除对应的计划任务。用户不需要额外操作，也不会留下半截记录。

失败处理：如果 UAC 被拒绝或删除失败，该任务在列表中被标记为「待清理」，并保留在配置中，下次启动时再次提醒。

第二级 · 机器级（主入口）

设置页与状态栏各有一个入口：「清理本机全部系统任务」。点击后进入清理向导：

第三级 · 应急（关键兜底）

为什么必须有这一级：归属表和配置文件都可能丢失。用户可能在几个月后换了一台电脑，想起「以前用 U 盘在旧电脑上设过关机任务」，但此时既没有 INI，也没有原始 U 盘。如果清理能力依赖本地数据，这种情况就永远清不掉了。

所以必须提供一个只依赖「任务名前缀 + 文件夹名」的清理命令，它不读任何配置文件，直接把 \PlanPower 文件夹连根拔起。

:: 清理本机全部 PlanPower 系统任务（不依赖配置文件）
PlanPower.exe /cleanup-all

:: 先预览将要删除的内容，不做实际删除
PlanPower.exe /cleanup-all /dry-run

:: 输出示例
::   发现 3 个系统任务：
::     \PlanPower\工作日下班关机_a1b2c3d4   关机  下次 今天 23:00
::     \PlanPower\早晨唤醒_e5f6a7b8         开机  下次 明天 08:30
::     \PlanPower\临时关机_c9d0e1f2         关机  已失效
::   已删除 3 个任务，\PlanPower 文件夹已移除。

补充 · 退出时自动清理

设置项，默认关闭。文案需要写清楚它和「持久」是互斥的：

✓
退出时自动清理本机系统任务
适合在别人的电脑上临时使用：用完即走，不留痕迹。
注意：开启后系统任务只在本次运行期间有效，「跨重启存活」将不再生效。

6动作兼容性矩阵

不是所有动作都能做成系统持久任务——任务计划程序的动作只能是「启动一个 exe」，而 Windows 并不为每种动作都提供了现成命令。

动作内存计时系统持久任务系统任务实际调用的命令说明
关机✅✅shutdown.exe /s /t N /c "提示"系统自带倒计时提示框
重启✅✅shutdown.exe /r /t N /c "提示"同上
休眠✅✅shutdown.exe /h需系统已启用休眠
注销✅✅shutdown.exe /l—
睡眠✅✅rundll32.exe powrprof.dll,SetSuspendState 0,1,0注意休眠陷阱

关闭显示器✅⚠️ 不支持无对应系统命令只能用窗口消息广播，无独立 exe 可调
关机前收尾动作✅⚠️ 不支持需 PlanPower 自身执行见下方说明

关于「⚠️ 不支持」的处理方式：这三种能力需要 PlanPower 自己运行才能实现，而系统任务的动作必须指向一个固定的 exe 路径——U 盘盘符会变，指向 U 盘上的 exe 不可靠。

方案：在向导中直接禁用这些组合。当用户为任务勾选了「收尾动作」或「看门狗」，任务类型自动锁定为「内存计时」，并给出说明：「收尾动作需要 PlanPower 运行才能执行，因此该任务无法注册为系统持久任务。」

不做「静默降级」——让用户明确知道限制在哪，比事后发现「为什么我的收尾脚本没跑」要好得多。

进阶选项 · 驻留副本（可选，默认不启用）

如果确实需要让「收尾动作」类任务也持久化，提供一个明确的进阶开关：

把 PlanPower 部署到本机

把 PlanPower.exe 复制到 %LOCALAPPDATA%\PlanPower\，系统任务指向这个副本。这样高级动作也能持久化，代价是：

  • 本机会多出一个约 300 KB 的文件
  • 副本不会自动更新，主程序版本升级后需要重新部署
  • 清理时需要一并删除这个副本（清理向导会自动处理）

这个选项藏在「高级」折叠区里，不主动推荐。绝大多数用户不需要它。

7异常场景处理

这些场景在实际使用中一定会遇到，必须提前定义好行为。

#场景检测方式处理策略
1 UAC 被用户拒绝 ShellExecuteEx 返回 ERROR_CANCELLED（1223） 任务保留为「未注册」状态，配置不丢；界面提示「已取消注册，任务仍以内存计时方式运行」。绝不静默失败。
2 配置说注册了，系统里却没有 枚举 \PlanPower 后比对 标记为「已失效」，提供「重新注册」按钮；若任务本应正在运行，同时在状态栏提示
3 系统里有，配置里没有（孤儿） 同上 不出现在主列表（避免干扰），但在清理向导中单独分组提示「发现 2 个不属于当前配置的任务，是否一并删除？」
4 任务被用户手动改动 比对任务的 XML 内容与配置 标记「外部修改」，提供「用配置覆盖」与「采纳系统版本」两个选项，不擅自覆盖
5 U 盘写保护，无法记录归属 写 INI 失败 注册仍然执行（任务本身有效），但立即弹出警告：「本次注册无法记录到配置，请手动记住并在离开前清理」
6 清理时部分任务删除失败 逐条检查 DeleteTask 返回值 失败项写入待清理列表，下次启动时再次提醒；提供失败原因（权限不足 / 任务被占用）
7 U 盘被拔出，程序仍在运行 文件操作返回 ERROR_ACCESS_DENIED / ERROR_NOT_READY 内存态继续运行至本次会话结束；关键操作立即落盘失败则转为内存态；退出时不报错
8 同一台机器插了两支不同的 U 盘 两份配置各自记录本机指纹下的任务列表 各自只管自己注册的任务；清理时按任务名前缀区分（任务名内含 U 盘标识段）
9 任务计划程序服务被禁用 ITaskService::Connect 失败 禁用「系统持久任务」选项并说明原因；内存计时功能不受影响
10 系统任务执行时用户未登录 —（预期行为） 任务以 LOCAL SYSTEM 身份运行，不依赖登录会话。这正是它比内存计时可靠的原因，在界面上作为卖点说明

场景 8 的细节设计：为避免两支 U 盘的任务互相误删，任务名中包含一段短标识：\PlanPower\工作日下班关机_{U盘标识}_{任务ID}。清理时只删自己标识的那批。这是「多盘共存」场景下保证安全的必要措施。

8技术实现要点

8.1 命名规范

// 任务名格式
\PlanPower\{用户可读名称}_{U盘标识4位}_{任务ID 8位}

// 示例
\PlanPower\工作日下班关机_a1b2_c3d4e5f6
\PlanPower\早晨唤醒_a1b2_9f8e7d6c

// 用户可读名称中的非法字符（ \ / : * ? " < > | ）需转义或替换
// 总长度限制在 200 字符内（任务名上限为 238 字符）

8.2 通过 COM 创建任务

// 连接任务计划程序服务（零第三方依赖，走系统注册的 COM 服务器）
ITaskService* pService = nullptr;
CoCreateInstance(CLSID_TaskScheduler, nullptr, CLSCTX_INPROC_SERVER,
                 IID_ITaskService, (void**)&pService);
pService->Connect(_variant_t(), _variant_t(), _variant_t(), _variant_t());

// 打开或创建 \PlanPower 文件夹
ITaskFolder* pFolder = nullptr;
pService->GetFolder(_bstr_t(L"\\PlanPower"), &pFolder);
if (!pFolder) pService->GetFolder(_bstr_t(L"\\"), &pRoot),
               pRoot->CreateFolder(_bstr_t(L"PlanPower"), _variant_t(), &pFolder);

// 定义任务
ITaskDefinition* pTask = nullptr;
pService->NewTask(0, &pTask);

// 注册信息
IRegistrationInfo* pReg = nullptr;
pTask->get_RegistrationInfo(&pReg);
pReg->put_Author(_bstr_t(L"PlanPower (portable)"));
pReg->put_Description(_bstr_t(L"由便携版 PlanPower 注册，可用 /cleanup-all 清理"));

// 以 LOCAL SYSTEM 身份运行 —— 无人登录时也生效
IPrincipal* pPrincipal = nullptr;
pTask->get_Principal(&pPrincipal);
pPrincipal->put_UserId(_bstr_t(L"S-1-5-18"));
pPrincipal->put_LogonType(TASK_LOGON_SERVICE_ACCOUNT);
pPrincipal->put_RunLevel(TASK_RUNLEVEL_HIGHEST);

// 关键设置 —— 这三个默认值最坑人，必须显式覆盖
ITaskSettings* pSet = nullptr;
pTask->get_Settings(&pSet);
pSet->put_DisallowStartIfOnBatteries(VARIANT_FALSE);   // 默认 TRUE，会让笔记本静默跳过
pSet->put_StopIfGoingOnBatteries(VARIANT_FALSE);      // 默认 TRUE
pSet->put_StartWhenAvailable(VARIANT_TRUE);           // 错过时间后开机补跑
pSet->put_WakeToRun(VARIANT_TRUE);                    // 可唤醒睡眠中的电脑
pSet->put_ExecutionTimeLimit(_bstr_t(L"PT5M"));

// 动作：指向系统固定路径的 shutdown.exe，而非 U 盘上的 PlanPower.exe
IActionCollection* pActions = nullptr;
pTask->get_Actions(&pActions);
IAction* pAction = nullptr;
pActions->Create(TASK_ACTION_EXEC, &pAction);
IExecAction* pExec = nullptr;
pAction->QueryInterface(IID_IExecAction, (void**)&pExec);

wchar_t shutdownPath[MAX_PATH];
GetSystemDirectoryW(shutdownPath, MAX_PATH);
wcscat_s(shutdownPath, L"\\shutdown.exe");          // 固定系统路径，永不失效

pExec->put_Path(_bstr_t(shutdownPath));
pExec->put_Arguments(_bstr_t(L"/s /t 60 /c \"系统将在 60 秒后关机\""));

// 注册到 \PlanPower 文件夹
IRegisteredTask* pRegistered = nullptr;
pFolder->RegisterTaskDefinition(_bstr_t(taskName), pTask, TASK_CREATE_OR_UPDATE,
                                _variant_t(), _variant_t(), TASK_LOGON_SERVICE_ACCOUNT,
                                _variant_t(L""), &pRegistered);

这段是当初的评估稿，最终实现有四处不同，都记在这里，免得后来的人照抄：

  1. 改用 XML，不用对象模型。逐层 get_/put_ 链长且每一步都可能失败，出错面大。现在拼 XML 字符串后交给 put_XmlText —— 「生成什么」变成纯函数，可以在没有 Windows 的机器上离线断言。
  2. 用 GetWindowsDirectoryW + System32，不用 GetSystemDirectoryW。后者在 64 位系统上被 32 位进程调用时会被 WOW64 重定向到 SysWOW64，那不是我们要的目录。
  3. RegisterTaskDefinition 之前必须先 put_XmlText。一步走的时候，XML 写错、权限不够、文件夹不存在、任务重名都返回同一个失败，报错只能写得很含糊——v0.2 那次「注册系统任务失败」查不出原因，就是吃了这个亏。拆成两步后，两阶段的失败文案不同，一眼能看出该查哪一边。
  4. 不要设 put_URI。任务路径本来就由注册时的第一个参数决定、服务端自己推导；手写一个以反斜杠开头的 URI，一旦与注册路径有任何出入就以 0x80041318 被整段拒绝，而报错完全指不到这个元素上。属于没收益、只有风险的字段。

8.3 清理实现

// 枚举并删除（不依赖任何本地配置）
IEnumWorkItems* pEnum = nullptr;
pFolder->GetTasks(TASK_ENUM_HIDDEN, &pEnum);

LPWSTR* names = nullptr;
ULONG fetched = 0;
while (pEnum->Next(1, &names, &fetched) == S_OK && fetched == 1) {
    pFolder->DeleteTask(names[0], 0);     // 0 = 不因正在运行而失败
    CoTaskMemFree(names[0]);
}

// 仅当文件夹为空时才删除文件夹本身，避免误删其他任务
pRoot->DeleteFolder(_bstr_t(L"PlanPower"), 0);

为什么用 TASK_ENUM_HIDDEN：如果不带这个标志，被隐藏的任务不会被枚举到，清理就会漏。而我们的任务在任务计划程序 GUI 里可能是隐藏状态，所以必须显式请求枚举隐藏项。

9验收标准

逐条可在虚拟机验证。

9.1 默认状态（不开启系统任务）

  • 零写入：全新运行、创建 5 条内存任务、正常退出。用 Process Monitor 检查，除自身配置文件外无任何系统写入，任务计划程序中不存在 \PlanPower 文件夹。
  • 无 UAC 打扰：全程不弹出任何 UAC 提示。
  • 干净退出：删除 exe 与配置文件后，机器上无任何残留。

9.2 开启系统任务后

  • 说明弹窗不可跳过：未勾选确认前，「启用」按钮为禁用状态。
  • 默认选项正确：创建向导中「内存计时」为默认选中项。
  • 注册成功可验证：创建一条系统任务后，在 Windows「任务计划程序」中能看到 \PlanPower 文件夹及对应任务，且「作者」字段为 PlanPower (portable)。
  • 关键设置生效：导出的任务 XML 中，DisallowStartIfOnBatteries 为 false、StartWhenAvailable 与 WakeToRun 为 true、UserId 为 S-1-5-18。
  • 动作路径正确：任务动作指向 %SystemRoot%\System32\shutdown.exe，不是 U 盘上的 exe。
  • 拔盘后仍生效：注册任务后完全退出程序并拔掉 U 盘，任务到点仍然执行。
  • UAC 拒绝不丢数据：在 UAC 弹窗点「否」，任务保留为「未注册」状态，配置未丢失，界面有明确提示。
  • 状态栏可见：状态栏正确显示「本机已注册 N 个系统任务」，点击可直达清理入口。

9.3 清理能力

  • 任务级清理：删除一条系统任务，任务计划程序中对应条目同步消失。
  • 一键清理：点击「清理本机全部系统任务」，确认后 \PlanPower 文件夹被完全移除。
  • 孤儿检测：手动在任务计划程序中创建一个 \PlanPower\测试任务（配置里没有），清理向导能识别并提示为孤儿任务。
  • 应急清理不依赖配置：删除 INI 文件后执行 PlanPower.exe /cleanup-all，仍能完整清理。
  • 干跑模式：/cleanup-all /dry-run 只列出将要删除的任务，不执行实际删除。
  • 归属识别：在机器 A 注册任务后，把配置复制到机器 B，机器 B 上正确显示「注册于 [机器 A 名]」且不可编辑。
  • 退出自动清理：开启该选项后退出程序，任务计划程序中不留任何 PlanPower 条目。

9.4 边界场景

  • 不支持的组合被拦截：为任务勾选「收尾动作」后，任务类型自动锁定为内存计时，并给出明确说明。
  • 任务计划程序被禁用：在组策略中禁用任务计划程序服务后启动，程序正常运行，系统任务选项被禁用并说明原因。
  • 多盘共存：两支 U 盘在同一台机器上各注册任务，清理时只删各自的那批，互不影响。
  • 中文与特殊字符：任务名含中文、空格、引号时，注册与清理均正常。
