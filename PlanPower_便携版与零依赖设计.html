Revision 2 · 便携版与零依赖专项设计

PlanPower 便携版

单文件、免安装、零依赖。复制到任意目录（含 U 盘）即可运行，不写注册表、不装运行库、不留残留。本文明确其功能范围、使用方式、运行环境要求，以及便携性与零依赖的具体保证手段。

修订技术栈 C++17 + Win32 API 静态链接 CRT（/MT） 目标体积约 300 KB 零子进程 · 零注册表

重要：本次需求推翻了 Revision 1 的技术选型。上一版推荐的 C# + WPF + .NET Framework 4.8 方案，在「免安装」这一项上是达标的，但在「不依赖系统组件」这一项上不达标——.NET Framework 是 Windows 的可选功能，可以在「启用或关闭 Windows 功能」中被禁用；Windows 10 1809 及更早版本预装的是 4.7.2 或更低，并不保证有 4.8。若用户的机器上恰好缺了这个组件，软件就直接起不来，这与「开箱即用」的目标冲突。

因此技术栈修订为 C++17 + Win32 原生 API + 静态链接 C 运行库。功能设计、界面设计、竞品调研、技术坑清单仍然沿用 Revision 1，本文只覆盖与便携性和零依赖相关的部分。

1需求边界澄清：什么叫「零依赖」

这一节必须先讲清楚，否则后面所有的技术决策都站不住脚。

「不依赖外部运行环境、第三方库或系统组件」这句话里，「不依赖系统组件」在技术上是不可能实现的。任何一个 Windows 程序的进程创建、内存分配、窗口绘制、文件读写，都必须调用 kernel32.dll、user32.dll、gdi32.dll——这些就是系统组件，且无法绕过（除非自己写操作系统）。

所以真正可执行、可验收的定义应该按依赖的性质来划分，而不是按「是不是系统提供的」来划分：

层级定义本方案说明
L1 免安装 不需要 setup / msi，复制文件即可运行；卸载 = 删除文件 ✅ 达成 单 exe，无安装程序、无卸载项
L2 无外部运行时 不需要用户额外安装或启用任何运行时、框架、运行库 ✅ 达成 排除 .NET / Python / Java / Node / VC++ Redist / WebView2
L3 无第三方库 不链接任何非微软官方发布的库，包括静态库与纯头文件库 ✅ 达成 零 NuGet、零 vcpkg、零 vendor 目录
L4 无系统 API 依赖 不调用任何 Windows 系统 DLL ❌ 不可能 技术上的伪命题，见上文说明

本方案采用的验收口径（建议以此为准）：

「不依赖任何需要用户额外安装、启用或配置的组件；只使用 Windows 安装完成后默认存在且无法卸载的核心系统库。」

按这个口径，依赖清单被严格约束为一张白名单（见 §7.2），凡是不在白名单里的 DLL，一律视为违规。

必须排除的「伪零依赖」陷阱

下面这些方案经常被当成「免安装」，但它们都不满足 L2：

方案为什么不合格
C# + .NET Framework 4.8属于 Windows 可选功能，可被禁用；Win10 1809 及更早版本不预装 4.8。用户机器上缺了就起不来
C# + .NET 8/9/10 自包含单文件运行时不缺，但体积 10–15 MB，且 NativeAOT 产物在部分配置下仍会依赖 MSVC 运行库
Python + PyInstaller 打包体积 15–40 MB，解包到临时目录，极易被 Windows Defender 启发式查杀（这是最典型的误报来源）
Electron / Tauri 套壳WebView2 在 Win10 上需要单独安装，Win11 才预装。直接违反 L2
PowerShell + WinForms 脚本启动慢、有控制台闪窗、脚本可被 ExecutionPolicy 拦截，且不是「软件」形态
MSVC 默认编译（/MD）会依赖 vcruntime140.dll + msvcp140.dll，目标机器没装 VC++ Redist 就直接报「缺少 DLL」。这是 C++ 便携版最常见的翻车点

2技术栈修订与论证

从 C# + WPF 改为 C++17 + Win32，这是一次「用开发成本换依赖纯度」的明确取舍。

选型结论：采用 C++17 + Win32 原生 API + 静态链接 CRT。

理由：这是唯一能同时满足 L1 + L2 + L3 且体积可控的方案。代价是 UI 需要手写 GDI 自绘，开发工作量约为 WPF 方案的 2–3 倍。考虑到界面结构并不复杂（一个列表、一个三步向导、一个悬浮窗、一个托盘菜单），这个代价是可控的。

2.2 编译配置（关键，决定了能不能做到零依赖）

:: 编译器
cl /std:c++17 /O2 /GS /GL /utf-8 ^
   /MT                      :: ★ 静态链接 CRT —— 零依赖的关键，绝不能用 /MD
   /DUNICODE /D_UNICODE ^     :: 全程宽字符，正确处理中文路径
   /DWIN32_LEAN_AND_MEAN ^
   /D_CRT_SECURE_NO_WARNINGS

:: 链接器
link /LTCG /OPT:REF /OPT:ICF ^
     /SUBSYSTEM:WINDOWS ^     :: 无控制台窗口
     /DYNAMICBASE /NXCOMPAT /HIGHENTROPYVA ^   :: 安全加固
     /MANIFEST:EMBED /MANIFESTINPUT:PlanPower.manifest ^
     kernel32.lib user32.lib gdi32.lib advapi32.lib shell32.lib ^
     comctl32.lib ole32.lib oleaut32.lib powrprof.lib shlwapi.lib ^
     /ENTRY:wWinMainCRTStartup

三个必须注意的编译期细节：

① /MT 必须与所有链接的静态库一致，若混入 /MD 编译的 .lib 会链接失败或运行时崩溃；

② 显式指定 /ENTRY:wWinMainCRTStartup（配合 /MT），避免因未定义 wWinMain 而误用控制台入口；

③ 资源（图标、字符串、UI 模板）全部编入 .rc，运行时不读取任何外部文件——这是「单文件」的硬要求。

2.3 目标架构：为什么建议发 x86

把主版本编译为 32 位（x86），可以得到最大的兼容性：

  • 在 64 位 Windows 10 / 11 上以 WOW64 方式原生运行，无性能问题（本程序不做重计算）
  • 在 32 位 Windows 上同样可运行——一个文件通吃
  • 在 Windows on ARM 设备上可通过 x86 模拟层运行

代价是：x86 进程受文件系统重定向影响（System32 会被重定向到 SysWOW64）。由于本程序不使用文件系统重定向敏感的路径，实际无影响。如果不需要兼容 32 位系统，也可以只发 x64 版本。

3.2 需要重新设计的功能

① 系统级持久任务 → 改为「显式可选 + 可一键清理」

冲突：「任务跨重启存活」需要写入 Windows 任务计划程序，这会污染宿主系统，与「便携、不留痕」直接矛盾。而且 U 盘拔走后，如果任务还留在那台机器上，就是残留。

解决：把它做成一个显式开关，默认关闭，并配套清理机制。

  • 默认状态：关闭。所有任务走内存计时引擎，完全不留痕，拔盘即消失。
  • 开启时：弹出说明，明确告知「将在本机任务计划程序中创建任务，离开本机前请点击『清理全部系统任务』」。需要 UAC 提权。
  • 便携模式专属选项：「退出时自动清理系统任务」——勾选后，程序退出即删除自己注册的全部系统任务，实现零残留。
  • 界面上用一个醒目的标记区分两类任务：内存任务（不留痕）与 系统任务（写入本机）。

② 开机自启 → 默认关闭，改为启动文件夹方式

冲突：便携版通常在 U 盘上，U 盘未必插着，「开机自启」意义不大；而且写 HKCU\...\Run 属于注册表污染。

解决：默认关闭。若用户显式开启，优先使用「启动」文件夹快捷方式（写文件，不写注册表），并在界面标注「本机专属设置，不会随 U 盘带走」。

③ 自动更新 → 取消

只读介质（部分 U 盘、光盘）无法自更新，且联网检查更新会引入隐私顾虑和杀软关注。便携版明确不提供自更新，改为在「关于」页展示版本号与手动下载地址。

④ 收尾动作中的「执行自定义脚本」→ 路径规则收紧

如果允许执行外部脚本，脚本路径必须是相对于 exe 目录的相对路径，运行时动态解析。绝不持久化绝对路径——否则换台机器盘符一变就失效。

3.3 明确不做

不做安装程序

没有 setup.exe、没有 msi、不写 Program Files、不创建卸载项。

不做 Windows 服务

注册服务需要写注册表且需要管理员权限，与便携目标冲突。

不做文件关联 / 右键菜单

这两者都必须写注册表，是典型的「安装行为」。

不做联网功能

不检查更新、不收集统计、不加载任何远程资源。

4使用方式

从拿到文件到跑起来，只有一步。

4.1 部署

把 PlanPower.exe 复制到任意位置，双击。没有别的步骤。

可以是桌面、D 盘某个文件夹、U 盘根目录、甚至网盘同步目录。程序不关心自己在哪，只关心自己旁边能不能写文件。

4.2 首次运行

  1. 双击 PlanPower.exe（不需要右键「以管理员身份运行」，除非你要注册系统任务）。
  2. 程序检测到没有配置文件，显示欢迎页，列出三个常用模板卡片：「下班关机」「下载完关机」「睡前休眠」。
  3. 底部显示当前存储位置（例如 E:\Tools\PlanPower\），并提供切换按钮。默认就写在 exe 同目录。
  4. 点任一模板卡片，或点「从零创建」，进入三步向导。
  5. 完成后窗口最小化到托盘，任务开始计时。

4.4 数据文件

默认情况下，程序运行后会在 exe 同目录产生以下文件（也可以一个都不产生，见 §6.2 的只读介质策略）：

E:\Tools\PlanPower\
├─ PlanPower.exe          ← 唯一的程序文件
├─ PlanPower.ini          ← 设置与任务定义（INI 格式，可用记事本编辑）
├─ logs\                  ← 执行日志（可在设置中关闭）
│   └─ 2026-10.log
└─ portable.flag          ← 可选：存在此文件则强制便携模式

为什么用 INI 而不是 JSON？人类可读、可以直接用记事本改、出问题时容易排查，而且格式本身简单到可以自己写解析器（约 300 行，含 UTF-16/UTF-8 编解码）。

每个任务写成一个 [Task.<n>] 段，字段扁平化存储，足以表达全部配置；本机归属表另开 [Host.<机器指纹>] 段。

为什么最终没用 kernel32 自带的 GetPrivateProfileStringW / WritePrivateProfileStringW？这两个 API 看着最省事，但有两个要命的性质：

  1. 进程内缓存整个文件的映射，写入先进缓存、延迟落盘。
  2. 缓存里会留着上一版的陈旧键值，所以「先 DeleteFile 再重写」这个手法对它无效——删掉的段会自己长回来。

而 PlanPower 的工作方式是：保存配置后立刻 ShellExecuteEx(runas) 拉起提权助手进程，助手从磁盘读同一个 INI。于是助手读到的要么是旧内容、要么文件根本还不存在。这就是 v0.2 那次真机反馈「注册系统任务失败」的主因——「找不到任务」被伪装成了「注册失败」。

现在改成自己实现（src/inifile.h / src/inifile.cpp）：整段拼好后写 PlanPower.ini.tmp → FlushFileBuffers → MoveFileExW(MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH) 原子替换。刷盘那一步不能省，它就是「跨进程可见性」的全部保障；原子替换保证读者要么看到旧的完整文件、要么看到新的完整文件。

格式仍然是 INI，仍然是 UTF-16LE + BOM，记事本照样能改——便携性与零依赖这两条约束一点没变：这一层只依赖 <string> / <vector>，不引入任何第三方库，也不增加任何运行时依赖。

4.5 卸载

  1. 如果开启过「系统任务」，先在主界面点「清理全部系统任务」（或手动在任务计划程序里删除 \PlanPower 文件夹）。
  2. 删除 PlanPower.exe 及其同目录的配置文件与日志目录。

完毕。没有注册表残留，没有 Program Files 残留，没有后台服务。

6便携性保证措施

便携不是一个口号，是一组必须逐条落实的工程约束。

6.1 路径解析：一切以 exe 所在目录为基准

这是便携化最基础也最容易被忽略的一条。从快捷方式、从命令行、从「以管理员身份运行」启动时，当前工作目录（CWD）都可能不是 exe 所在目录。所以：

// ✅ 正确：取 exe 自身的完整路径，取其目录作为基准
wchar_t exePath[MAX_PATH];
GetModuleFileNameW(nullptr, exePath, MAX_PATH);
wchar_t* lastSlash = wcsrchr(exePath, L'\\');
if (lastSlash) *(lastSlash + 1) = L'\0';   // 得到 "E:\Tools\PlanPower\"

// ❌ 错误：CWD 不可靠，可能是 C:\Windows\System32
// GetCurrentDirectoryW(MAX_PATH, buf);

所有配置文件、日志、模板路径一律由这个基准目录拼接得出，绝不使用相对路径直接访问文件。

6.2 存储位置决策树

程序启动时按以下顺序决定配置写到哪，并把结果显示在界面状态栏上（用户随时知道自己的数据在哪）：

6.3 便携性工程约束清单

#约束具体做法
1单文件发布图标、字符串表、任务模板、UI 资源全部编入 .rc；运行时零外部文件读取
2路径基准统一由 GetModuleFileNameW 推导，禁用 CWD
3不写注册表默认配置下对注册表只读（仅读取系统信息，不写入）。「开机自启」用启动文件夹而非 HKCU\Run
4不写系统目录不触碰 Program Files、System32、Windows 目录
5盘符漂移免疫绝不持久化绝对路径。任务内引用的外部程序一律存相对路径，运行时基于 exe 目录解析
6只读介质降级启动时探测可写性；不可写则全部配置仅存内存，退出时提示「本次改动未保存」
7多实例隔离命名互斥体 Local\PlanPower_<exe目录哈希>——按目录隔离，U 盘在不同机器上可各跑各的，不互相干扰
8系统任务可清理提供「清理全部系统任务」按钮；可勾选「退出时自动清理」实现零残留
9日志可关闭默认写日志，可关闭或限制大小——U 盘闪存有写入寿命，长时间运行需谨慎
10可移动介质感知用 GetDriveTypeW 检测运行目录是否为 DRIVE_REMOVABLE；若是，则关键操作（创建任务、修改设置）立即落盘而非延迟写入
11拔出容错可移动介质上运行时，所有文件操作包在异常处理里；写入失败不崩溃，转为内存态并提示
12无自更新不下载、不替换自身文件（只读介质无法替换）
13首次运行引导无配置文件时展示欢迎页与模板，而非空白界面
14存储位置可见状态栏常驻显示当前实际存储路径，用户随时可确认数据在哪

一句话总结便携性设计：程序把自己的位置当作唯一的世界中心，除此之外不往任何地方写东西。拔掉盘，这台机器上除了（可选的）几个计划任务之外，什么都没有留下。

7零依赖保证措施

零依赖不能靠自觉，要靠编译配置 + 白名单 + 构建期自动校验三重保障。

7.1 编译期措施

措施做法解决的问题
静态链接 CRT/MT（Release 与 Debug 都要，且与所有 .lib 一致）消除 vcruntime140.dll / msvcp140.dll 依赖——这是 C++ 便携版最常见的翻车点
不使用 MFC / ATL直接用 Win32 API，不用 afxwin.h / atlbase.h避免引入 MFC 相关 DLL
零第三方库不链接任何非系统 .lib；连 header-only 库也不用（自己写约 300 行 INI/JSON 处理）避免隐藏的传递依赖
内嵌 manifest/MANIFEST:EMBED 写入 Common Controls 6.0、DPI 感知、asInvoker 执行级别无需外置 .manifest 文件；同时解决界面视觉样式与 DPI 模糊
安全与体积优化/O2 /GL /LTCG /OPT:REF /OPT:ICF + /DYNAMICBASE /NXCOMPAT /HIGHENTROPYVA减小体积的同时保留 ASLR / DEP 加固
不使用 UPX 压缩即使能进一步缩小体积也不压缩UPX 加壳是杀软启发式误报的高危特征，得不偿失

7.4 向下兼容策略

若需要兼容 Windows 7 / 8.1，需遵守两条约束：

  • 只调用 Win7 时代就存在的 API。涉及 SetThreadDpiAwarenessContext、GetDpiForWindow 等 Win10 新增函数时，用 GetProcAddress 动态加载并做存在性判断，而不是静态导入——静态导入会让程序在旧系统上直接启动失败。
  • manifest 中的 <dpiAwareness> 用旧写法，或同时声明新旧两套。

如果不打算兼容 Win7，可以把系统要求直接定为 Windows 10 1607+，代码可以简单不少。

7.5 关于提权：唯一不可避免的子进程

「零子进程」是本方案的默认状态，但有一个例外：UAC 提权在 Windows 机制上必须通过启动新进程实现，无法绕过。使用 ShellExecuteEx + runas 动词时，会由系统拉起一个提权后的新实例。

这不影响零依赖结论——提权后的实例就是同一个 exe 自己，不涉及任何外部程序。而且这条路径只在用户主动开启「注册系统任务」功能时才会走到。

8.1 关机：InitiateSystemShutdownExW 的两个额外好处

// 1) 先提升关机特权（标准用户默认拥有 SeShutdownPrivilege，这里只是确保生效）
HANDLE hToken;
OpenProcessToken(GetCurrentProcess(), TOKEN_ADJUST_PRIVILEGES | TOKEN_QUERY, &hToken);
TOKEN_PRIVILEGES tp = {};
tp.PrivilegeCount = 1;
LookupPrivilegeValueW(nullptr, SE_SHUTDOWN_NAME, &tp.Privileges[0].Luid);
tp.Privileges[0].Attributes = SE_PRIVILEGE_ENABLED;
AdjustTokenPrivileges(hToken, FALSE, &tp, 0, nullptr, nullptr);
CloseHandle(hToken);

// 2) 发起关机：超时 60 秒，系统会弹出带倒计时的官方提示框
InitiateSystemShutdownExW(
    nullptr,                              // 本机
    L"系统将在 60 秒后关机，请保存工作",      // 提示文本（最长 512 字符）
    60,                                 // 倒计时秒数
    FALSE,                              // 是否强制关闭应用（FALSE = 优雅）
    FALSE,                              // 关机后是否重启
    SHTDN_REASON_MAJOR_APPLICATION | SHTDN_REASON_FLAG_PLANNED);

两个关键收益：

① 系统自带倒计时提示框。调用后 Windows 会弹出官方的关机倒计时窗口并显示自定义文本。这意味着即使 PlanPower 完全没在运行，用户也依然能看到提示并有机会取消（通过界面按钮或 AbortSystemShutdownW）。这正好补上了 Revision 1 里「主程序没运行就没有提醒」的短板。

② 零子进程。不启动 shutdown.exe，因此不受组策略禁用该 exe 的影响，也不会因为「频繁启动系统关机程序」而触发杀软的启发式规则。

8.2 一个必须讲清楚的架构约束

系统计划任务的动作只能是「启动一个 exe」——这是任务计划程序本身的机制，无法绕过。所以当用户启用「系统任务」功能时，注册进去的任务动作必须指向一个真实存在的可执行文件。

这里有个陷阱：如果指向 U 盘上的 PlanPower.exe，盘符一变任务就失效；而且 U 盘拔掉后任务彻底无法执行。

解决方案：系统任务的动作指向 %SystemRoot%\System32\shutdown.exe——系统绝对路径、永不变化、任何 Windows 都有。PlanPower 只负责注册和管理这些任务，不参与执行。

这样带来三个好处：任务不依赖 PlanPower 存在；U 盘拔掉后任务照样按期执行；这也正是「任务跨重启存活」这一承诺的真实含义。

注意：这不是 PlanPower 自己 spawn 的进程，而是由操作系统调度器调起的系统自带程序，不影响「零依赖」的结论——shutdown.exe 是 Windows 核心组件且路径固定。

9.1 零依赖验收

  • 依赖表检查：dumpbin /dependents PlanPower.exe 的输出仅含 §7.2 白名单内的 DLL，无 vcruntime140.dll、无 msvcp140.dll、无任何第三方 DLL。
  • 裸机运行：在全新安装、未装任何运行库的 Windows 10 虚拟机上双击 exe，界面正常弹出，无「缺少 xxx.dll」报错。
  • 无控制台窗口：双击运行时没有黑色命令行窗口闪现。
  • 体积达标：单文件体积小于 512 KB。
  • 冷启动速度：从双击到界面可见，耗时小于 100 ms。
  • 无子进程：程序运行期间，在任务管理器中展开其进程树，没有子进程（提权场景除外）。

9.2 便携性验收

  • U 盘漫游：复制到 U 盘，在机器 A 上创建 3 条任务并退出；把 U 盘插到机器 B（盘符不同），程序能正常读取全部任务与设置。
  • 只读介质：把程序目录设为只读（或使用带写保护开关的 U 盘），程序仍能启动并正常工作，配置改动仅存内存，退出时给出明确提示。
  • Program Files 场景：把 exe 放进 C:\Program Files\（无写权限），程序自动降级到 %LOCALAPPDATA%\PlanPower\ 并在状态栏标注「非便携模式」。
  • 路径独立性：从「以管理员身份运行」启动（此时 CWD 为 System32），配置文件仍正确写在 exe 同目录，而非 System32。
  • 零注册表：用 Process Monitor 全程监控，除读取外无任何注册表写入（筛选 RegSetValue 结果为空）。
  • 零系统目录写入：Process Monitor 中无对 Program Files / Windows / System32 的写操作。
  • 可移动介质识别：在 U 盘上运行时，状态栏正确显示「可移动介质」标识，关键配置实时落盘。
  • 拔出容错：运行中强制拔出 U 盘，程序不出现未捕获异常弹窗，优雅降级或正常退出。
  • 多实例隔离：同一台机器上从两个不同目录运行两份 PlanPower，互不干扰，各自管理自己的任务。
  • 卸载零残留：未启用系统任务时，删除 exe 与配置文件后，机器上无任何残留（注册表、临时目录、缓存均为空）。
  • 系统任务清理：启用系统任务后，点击「清理全部系统任务」，任务计划程序中 \PlanPower 文件夹被完全移除。

10已知限制与风险

#限制 / 风险性质应对
1 系统计划任务的动作必须调用外部 exe（shutdown.exe） OS 机制限制，无法规避 指向 %SystemRoot%\System32\shutdown.exe 这个固定系统路径；不影响零依赖结论
2 UAC 提权必须启动新进程 OS 机制限制 仅「注册系统任务」这一可选功能会触发；启动的是自身 exe，不涉及外部程序
3 杀软启发式误报：小体积未签名 exe + 调用关机 API 外部环境风险 不用 UPX 加壳、不联网、不写系统目录、不创建计划任务（除非用户主动开启）；有条件时做代码签名
4 便携版无法自更新 设计取舍 只读介质无法替换自身文件；改为在「关于」页显示版本与手动下载入口
5 系统任务会留在宿主机器上 设计取舍 默认关闭该功能；开启时明确告知；提供「退出时自动清理」实现零残留
6 组策略禁用关机 API / 权限被收紧（企业环境） 环境限制 启动时探测可用通道并自动降级（InitiateSystemShutdownExW → ExitWindowsEx），无法执行时给出明确原因而非静默失败
7 U 盘闪存写入寿命 硬件特性 日志默认限制大小并可关闭；配置仅在变更时写入，不做周期性落盘
8 UI 开发成本显著高于 WPF 方案 工程成本 界面结构本身不复杂（列表 + 向导 + 悬浮窗 + 托盘）；业务逻辑层与界面层严格分离，未来若要改回托管方案可复用
9 无管理员权限时无法注册系统任务 权限限制 界面上清晰区分「内存任务」与「系统任务」，并说明后者需要提权

总体评价：这次修订用「UI 开发成本」换来了「依赖纯度的确定性」。对于一个主打「复制即用、不挑机器」的便携工具来说，这个交换是划算的——用户不会关心你的界面是 XAML 还是 GDI 画的，但一定会因为「缺少 vcruntime140.dll」而放弃使用。
