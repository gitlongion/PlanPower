## 快速开始

### 方式一：直接运行（推荐）

把 `build/PlanPower.exe` 复制到任意位置，双击。没有安装步骤。

### 方式二：自己编译

**Windows（MSVC）** — 在「x64 Native Tools Command Prompt for VS」中：

```bat
build_msvc.bat
```

**macOS / Linux（MinGW-w64 交叉编译）** — 需先 `brew install mingw-w64`：

```bash
chmod +x build_mingw.sh
./build_mingw.sh
```

如果用的是免安装的 LLVM-MinGW（本机就是这么做的），用 `MINGW_BIN` 指定工具链目录即可：

```bash
export MINGW_BIN="$HOME/.workbuddy-ai/toolchains/llvm-mingw-20261006-ucrt-macos-universal/bin"
./build_mingw.sh
```

这个脚本除了出包，还会顺手跑一遍宿主机自检（见下文「构建验证结果」）。

两种方式产出的都是单文件 `PlanPower.exe`，运行时只依赖 Windows 核心系统库。

## 已实现的功能

### 七种电源动作

| 动作 | 实现方式 | 是否需要提权 |
|---|---|---|
| 关机 | `InitiateSystemShutdownExW` | 否 |
| 重启 | `InitiateSystemShutdownExW` | 否 |
| 睡眠 | `SetSuspendState(FALSE,...)` | 否 |
| 休眠 | `SetSuspendState(TRUE,...)` | 否 |
| 注销 | `ExitWindowsEx(EWX_LOGOFF)` | 否 |
| 锁定 | `LockWorkStation()` | 否 |
| 关闭显示器 | 广播 `WM_SYSCOMMAND` + `SC_MONITORPOWER` | 否 |

全部直接调用系统 API，**不启动任何外部进程**（不调用 `shutdown.exe`）。

### 四种触发方式

- **倒计时** — N 小时 N 分钟后执行
- **指定时刻** — 可以指定具体日期（年 / 月 / 日 + 时 / 分）；不填日期则沿用旧规则「今天这个点，已过顺延到明天」
- **每天** — 每日固定时间
- **每周** — 选定星期几的固定时间

### 任务管理

- 创建 / 编辑 / 删除 / 启用 / 停用
- **全部暂停 / 全部启用**（托盘菜单，系统任务只弹一次 UAC）
- 立即执行一次（不改动原有排期）
- 行内开关，点击即时生效
- 筛选：全部 / 运行中 / 已停用
- 键盘操作：↑↓ 选行、Home / End 跳首尾、空格切换开关、回车编辑、Delete 删除
- 重名提示（只提醒，不禁止）
- **执行历史**：读 `logs\` 里的日志，显示最近 300 条

### 两种执行方式

新建任务时二选一：

| | 内存计时（默认） | 系统持久任务 |
|---|---|---|
| 执行者 | PlanPower 自己 | Windows 任务计划程序 |
| 生效条件 | 程序必须运行 | 关掉程序、拔掉 U 盘、没人登录也照常执行 |
| 提前提醒 | 本程序弹置顶提醒窗 | 换成 `shutdown /t N`，即 Windows 官方关机倒计时 |
| 提权 | 不需要 | 每次写入 / 删除 / 启停都要过一次 UAC |
| 残留 | 无 | 在本机留下系统任务（可一键清理） |

**「关闭显示器」不支持系统任务。** Windows 没有对应的命令行入口，这一项只能由 PlanPower 运行时执行。编辑器会直接禁用该组合并说明原因，不做静默降级。

**两类任务不会同时执行。** 系统持久任务不会进入内存计时器——它的执行者是 Windows。早期版本两边都排，结果内存这条到点用 `timeout=0` 立刻执行，把 `shutdown.exe /t N` 争来的宽限窗口当场掐掉，提醒窗上的「取消本次」也变成谎话。

### 系统级持久任务的三道闸门

设计口径是「显式可选 + 可一键清理」，默认状态下程序**一个字节都不往宿主机写**：

1. **全局开关**（设置页，默认关）——首次开启会弹说明框，列出好处与代价；「启用」按钮在勾选「我已了解以上内容」之前一直是灰的，不能一路回车跳过。
2. **任务级选择**（编辑器「执行方式」行）——默认选「内存计时」。
3. **每次写入弹一次 UAC** —— 刻意没有做「一次提权、全程免打扰」。用户对「正在往系统里写东西」始终有感知。

三级清理：

| 级别 | 入口 | 说明 |
|---|---|---|
| 任务级 | 删除 / 取消勾选系统任务时 | 同步删除对应的系统任务 |
| 机器级 | 设置页「清理本机系统任务」 | 清空本机 `\PlanPower` 文件夹下全部任务 |
| 应急级 | `PlanPower.exe /cleanup-all` | 不读任何配置文件，只认 `\PlanPower` 这个约定 |

**失败路径是原子的。** 如果用户拒绝 UAC 或写入失败：

- 把系统任务**降级**为内存计时 → 整体中止保存，任务保持原样（否则会留下一条界面上看不见、后台却照常执行的任务）
- 把内存任务**升级**为系统任务 → 本地任务按内存计时保存，提示可重试（不让用户白填的参数丢掉）
- **删除**系统任务 → 本地记录不删（同理，避免留下管不到的系统任务）

系统任务命名规范 `\PlanPower\{可读名称}_{介质标识}_{任务ID前8位}`。介质标识取 exe 所在卷的序列号后 4 位十六进制，两支 U 盘插同一台机器也不会撞名。写入本机后记入 INI 的 `[Host.<机器指纹>]` 段，作为归属表；但这只是优化项，真正的兜底是任务名前缀和 `\PlanPower` 文件夹。

### 执行前提醒

默认提前 60 秒弹出置顶提醒窗（可配置，0 = 不提醒），显示实时倒计时与进度条，提供「取消本次」与「立即执行」。

系统持久任务下这一项的含义会变成 `shutdown /t N` 的倒计时宽限，标签会跟着改成「倒计时宽限（秒，0 = 立即执行）」；对于不认这个参数的动作（睡眠 / 休眠 / 注销 / 锁定）则标注为不支持。

### 设置

点击主窗口右上角的齿轮：

- **开机自动启动** —— 写入当前用户的启动项（`HKCU\...\CurrentVersion\Run`），只影响这台电脑，取消勾选即删除
- **开机启动时只显示托盘图标** —— 只在自启动那一次生效，不弹主界面；没开自启时这一项置灰
- **记录执行日志** —— 记到 exe 同目录的 `logs\`，按月分文件。UTF-16LE 带 BOM，记事本直接打开不乱码
- **日志保留月数** —— 默认 6，可填 0–120；0 表示不自动清理。只删严格符合 `YYYY-MM.log` 的文件
- **托盘快捷关机时长** —— 三个分钟数，逗号分隔（默认 `30,60,120`），读出来夹到 1–1440
- **系统级持久任务** —— 全局闸门 + 清理按钮 + 本机实际注册数量（以任务计划程序为准，不是数我们自己的标记）
- **存储** —— 显示配置文件完整路径与当前模式，可一键打开所在文件夹

### 系统托盘

- 右键菜单：三个可配时长的快捷关机、取消全部进行中的任务、暂停全部 / 启用全部、立即睡眠、锁定工作站、执行历史、打开主界面、退出
- 悬停提示实时显示最近一次任务的剩余时间
- 关闭主窗口 = 最小化到托盘；托盘「退出」才真正结束（有任务在计时会先确认）

### 便携性

- **单文件**，无外部资源文件
- **默认不写注册表**（唯一例外：用户主动勾选「开机自动启动」时写一条 Run 项，取消即删）
- **默认不写宿主机**（系统级持久任务默认关闭，开启后每次写入都要过 UAC）
- **配置写在 exe 同目录**的 `PlanPower.ini`（INI 格式，可用记事本直接编辑）
- 同目录不可写时（如放在 `Program Files`）自动降级到 `%LOCALAPPDATA%\PlanPower\`，状态栏会标注「用户目录模式」
- 存在 `portable.flag` 文件或命令行带 `/portable` 时强制便携模式
- 按 exe 目录哈希隔离互斥体，同一台机器上不同目录的副本互不干扰

### 高 DPI

按系统 DPI 缩放全部界面元素，在 100% / 125% / 150% / 200% 下均正常。

## 命令行接口

除了双击运行，同一个 exe 还带这几个开关（不需要单独的小工具）：

| 命令 | 用途 |
|---|---|
| `/cleanup-all` | 应急清理：删掉本机 `\PlanPower` 下全部系统任务并移除文件夹。不读任何配置文件 |
| `/sched-selftest` | 系统任务自检：为全部已启用任务生成 XML 并校验，结果写入 `PlanPower_selftest.txt` |
| `/dump-xml <ini> <任务ID>` | 导出任务定义（UTF-16LE + BOM），可直接喂给 `schtasks /create /xml` |
| `/portable` | 强制便携模式 |
| `/tray` | 启动后不显示主界面，只留托盘图标。**由自启动的 Run 项带过来**，手动双击永远不带 |
| `/sched-add` `/sched-del` `/sched-enable` `/sched-disable` | 内部使用：提权助手进程的入口，由主进程通过 `ShellExecuteEx(runas)` 拉起 |

这些分支**在处理单实例互斥体之前**分发——否则提权进程一启动就会撞上主进程已持有的互斥体，被当成「第二次启动」直接退出。

## 零依赖的实现方式

| 措施 | 说明 |
|---|---|
| 静态链接 CRT | MSVC 用 `/MT`；MinGW 用 `-static -static-libgcc -static-libstdc++` |
| 不使用 MFC / ATL | 只用 Win32 原生 API |
| 不使用第三方库 | 含 header-only 库；INI 读写自己实现（见下方「为什么不用 Profile API」） |
| 图标运行时绘制 | 用 GDI 生成，不引入 `.ico` 资源文件 |
| 不依赖 msimg32 | 渐变用逐行 `FillRect` 手绘 |
| 零子进程（主路径） | 全部电源动作走 API 直调，不 spawn 外部 exe |
| 零注册表写入（默认） | 配置只落文件；唯一例外是用户主动开启的开机自启 |
| 任务计划程序走 COM | 用 `ITaskService` + `put_XmlText` + `RegisterTaskDefinition`，不调 `schtasks.exe` |

> **系统任务的动作只能是「启动一个 exe」**，所以持久任务必须指向 `%SystemRoot%\System32\shutdown.exe`（固定系统路径），不能指向 U 盘上的 `PlanPower.exe`。这也是持久模式下提前提醒会变成 Windows 官方倒计时对话框的原因。
>
> 取 `System32` 目录用的是 `GetWindowsDirectoryW` 而不是 `GetSystemDirectoryW`——后者在 64 位系统上被 32 位进程调用时会被 WOW64 重定向到 `SysWOW64`。

### 为什么不用 kernel32 的 Profile API

`GetPrivateProfileString` / `WritePrivateProfileString` 看着最省事，但它有两个要命的性质：

1. **进程内缓存整个文件的映射，写入先进缓存、延迟落盘。**
2. **缓存里会留着上一版的陈旧键值**，所以「先 `DeleteFile` 再重写」这个手法对它无效——删掉的段会自己长回来。

而 PlanPower 的工作方式是：保存配置后**立刻** `ShellExecuteEx(runas)` 拉起提权助手进程，助手从**磁盘**读同一个 INI。于是助手读到的要么是旧内容、要么文件根本还不存在，`FindById` 返回空 —— 这就是 v0.2 那次「注册系统任务失败」的主因。

所以配置读写改成自己实现，落在 `src/inifile.h` / `src/inifile.cpp`：

| 环节 | 做法 |
|---|---|
| 写 | 整个文件在内存里拼好 → 写 `PlanPower.ini.tmp` → **`FlushFileBuffers`** → `MoveFileExW(MOVEFILE_REPLACE_EXISTING \| MOVEFILE_WRITE_THROUGH)` 原子替换 |
| 读 | 一次 `ReadAllBytes` 读完 → 按 BOM 识别 UTF-16LE / UTF-16BE / UTF-8 → 失败再退 ANSI 代码页 |
| 格式 | 仍是 INI，仍是 UTF-16LE + BOM，记事本照样能改 |

`FlushFileBuffers` 这一步**不能省**，它就是「跨进程可见性」的全部保障。替换用 `MoveFileExW` 是为了让读者要么看到旧的完整文件、要么看到新的完整文件，不会撞上写了一半的内容。

这一层刻意只依赖 `<string>` / `<vector>`，不碰任何 Windows API，所以能直接在 macOS 上编译并跑 112 项断言（见下文自检 1/3）。

### 运行时依赖清单（实测结果）

**x86 版（MinGW / UCRT 工具链）实际导入表：**

```
KERNEL32.dll   USER32.dll    GDI32.dll     ADVAPI32.dll
SHELL32.dll    COMCTL32.dll  ole32.dll     POWRPROF.dll
api-ms-win-crt-*.dll（10 个，即 Windows 通用 C 运行库 UCRT 的 API Set）
```

**关于 `api-ms-win-crt-*` 的说明：**

MinGW-w64 工具链链接的是 UCRT（Windows 通用 C 运行库），它从 **Windows 10 起就是操作系统自带组件**，位于 `System32`，不需要用户安装任何东西。所以对目标系统 Windows 10/11 而言，这是合格的零依赖。

但如果要向下兼容 **Windows 7 / 8.1**，需要用户预先安装 KB2999226（Universal C Runtime 更新）。**用 MSVC 的 `/MT` 编译则完全没有这个问题**——静态 CRT 不含任何 UCRT 依赖，导入表更干净。这也是 `build_msvc.bat` 存在的原因。

用 `dumpbin /dependents` 或 `objdump -p` 验证，出现清单之外的 DLL 即为缺陷。

### 宿主机自检（每次构建自动跑）

macOS 上跑不了 exe，Windows 的运行期行为没法在这里验证。但下面四件事可以在宿主机上验：

**1/4 配置文件的解析与编解码** —— `tools/initest.cpp` 直接编译**真实的** `src/inifile.cpp`，覆盖解析、换行兼容、畸形行、重复键、整数解析边界、UTF-16/UTF-8 编解码、严格 UTF-8 拒绝非法序列、以及「照抄 `TaskStore::Save()` 输出格式的整段配置」的写入—读回往返。

```
通过 112 项，失败 0 项
```

**2/4 任务 XML 生成** —— `tools/xmltest.cpp` 直接编译**真实的** `src/sched_xml.cpp`，只把时间、系统目录、介质标识、机器指纹、用户 SID 换成固定值，跑的是将来在 Windows 上真正执行的那份代码。`tools/hostshim/windows.h` 是最小化的假 `windows.h`（含 Hinnant 的 civil-date 算法），让纯逻辑模块能在 macOS 上编译运行。

覆盖两套定义：**完整版**（`version 1.2` + `Principals` + 全套 `Settings`）与**精简版**（`version 1.4` + 无 `Principals` + 只留会改变行为的项）。两套都要验——精简版是降级链的兜底，它写坏了等于把「注册失败」换成「注册成一条行为不对的任务」，比直接失败更糟。

再用 Python 的 `ElementTree` 解析真实代码导出的 14 个 `.xml`（7 个完整版 + 7 个精简版），做第二层结构与语义校验，包括「`Settings` 子元素是否全在 schema 允许集内」和「精简版是否真的省掉了冗余项」。

```
通过 130 项，失败 0 项
XML 解析与结构校验：通过 433 项，失败 0 项
```

**3/4 界面布局几何与行为不变量** —— `tools/check_layout.py` 把 `ui.cpp` 里的布局算术复刻一遍，检查四种触发方式下「无越界、无重叠」，并且 `LayoutEditor` 走完的 y 必须等于 `EditorClientHeight(kind)`。

更重要的是那几组**不变量检查**，它们编码的是踩过的坑：

- 创建过的每一个带 ID 的控件，是否都在可见性块里被显式声明过（防止「提前提醒输入框凭空消失」重演——当时的成因就是控件创建了却没有任何一处 `ShowWindow`）

## v0.2.1 修复记录

### 症状

在编辑器里选「系统持久任务」保存，弹窗提示 **注册系统任务失败**，任务写不进去。

### 排查

`SchedDoAdd` 里**所有**失败分支共用同一个标题，所以「服务连不上」「配置里找不到这个任务」「服务端拒绝这段 XML」三种完全不同的原因长得一模一样，报错本身没有信息量。顺着调用链往下看，发现两个叠加的问题：

**主因 — 配置还没落盘，提权助手就去读了。**

`TaskStore::Save()` 当时用的是 kernel32 的 Profile API：

```cpp
DeleteFileW(path_.c_str());          // 先删旧文件
IniWriteInt(L"General", ...);        // 然后是 WritePrivateProfileStringW
```

`WritePrivateProfileString` 写的是**进程内缓存**，延迟落盘，全程没有 flush。父进程保存完立刻 `ShellExecuteEx(runas)` 拉起提权助手，助手从磁盘读 INI —— 读到的要么是旧内容，要么文件还不存在，于是 `FindById(taskId)` 返回空。**「找不到任务」被伪装成了「注册系统任务失败」。**

更麻烦的是缓存里还留着上一版的键值，让「先删文件再重写」这个手法也失效。

**次因 — `RegistrationInfo` 里的 `<URI>`。**

`<URI>\PlanPower\xxx</URI>` 是照着导出样例加的，但任务路径本来就由 `RegisterTaskDefinition` 的第一个参数决定、服务端自己推导。手写一个以反斜杠开头的 URI，一旦与注册路径有任何出入，就会以 `0x80041318`（XML 取值非法）被整段拒绝，而报错完全指不到这个元素上。属于「没收益、只有风险」的字段，直接删掉。

### 修复

## v0.2.2 修复记录

### 症状

v0.2.1 之后真机复测，仍然保存失败，但这次的报错信息明确得多：

```
错误码：0x80041318
系统说明：任务 XML 包含一个格式不正确或超出范围的值
```

`0x80041318` 是 `SCHED_E_INVALIDVALUE`。它是**取值**错误，不是结构错误——`SCHED_E_UNEXPECTEDNODE`（多了元素）和 `SCHED_E_NAMESPACE`（命名空间不对）都是另外的码。

### 为什么这次不再靠猜

把生成的 XML 逐项对着 Task Scheduler 的 schema 核了一遍（元素层级、`Settings` 子元素顺序、各元素的取值域、`xs:sequence` 与 `xs:all` 的区别），**没有找到确定性的违规**。原因是 `SCHED_E_INVALIDVALUE` 名下还有一部分约束文档里没写、只能实测：它同时取决于**服务端版本**、**注册身份**，以及若干历史遗留的取值口径（微软自己的文档在 `LogonType` 元素页上就只列了 `S4U` 和 `InteractiveToken` 两个值，而 `ServiceAccount`、`Password` 明明在广泛使用）。这类问题在 macOS 上无法复现。

所以 v0.2.2 换了思路：**不再试图猜中唯一的正确写法，而是把几种「都合法但服务端口味不同」的写法按优先级试一遍，并把每一次的结果完整记录下来。**

### 四条改动

**1. 定义分成两套，按顺序降级重试**（`src/sched_xml.cpp` / `src/sched.cpp`）

| 顺序 | 定义 | `version` | `Principals` | `Settings` | `userId` 参数 |
|---|---|---|---|---|---|
| 1 | 完整 | 1.2 | 有 | 全套 | 账户名 |
| 2 | 完整 | 1.4 | 有 | 全套 | 账户名 |
| 3 | 完整 | 1.2 | 有 | 全套 | SID |
| 4 | 精简 | 1.4 | 无 | 只留语义项 | 账户名 |
| 5 | 精简 | 1.4 | 无 | 只留语义项 | SID |

前三条**语义完全一致**，差别只在可能被服务端挑剔的写法上，所以谁先成功都不影响行为。第四条起是兜底。

重试全部发生在**同一个提权进程**里，不会重复弹 UAC。

**2. 降级不能悄悄改坏行为**（这条最要紧）

精简定义去掉的必须都是**等于服务端默认值**的冗余项：`AllowHardTerminate`（默认 true）、`RunOnlyIfNetworkAvailable`（默认 false）、`IdleSettings`（只在 `RunOnlyIfIdle=true` 时才有意义）、`AllowStartOnDemand`（默认 true）、`Hidden`（默认 false）、`RunOnlyIfIdle`（默认 false）、`Priority`（默认 7）。

而下面这些**两套定义都必须逐字写出**，因为它们会改变行为：

| 设置 | 值 | 不写的后果 |
|---|---|---|
| `DisallowStartIfOnBatteries` | `false` | 默认 `true`，笔记本用电池时**静默不执行**且毫无报错 |
| `StopIfGoingOnBatteries` | `false` | 默认 `true`，一插拔电源就中断 |
| `StartWhenAvailable` | `true` | 默认 `false`，到点时机器关着就**不再补跑** |
| `WakeToRun` | `true` | 默认 `false`，不能唤醒休眠中的机器 |
| `Enabled` | 用户设定 | 启停开关失效 |
| `ExecutionTimeLimit` | `PT10M` | 默认 `PT72H`，卡住的实例在系统里挂三天 |

换句话说：降级只允许「把默认值重复一遍」的部分变少，**不允许承诺的功能变少**。如果降级把行为改坏了，那比直接失败更糟——用户会得到一条看起来正常、实际不对的任务。这条已经写成断言（见下文 E18）。

**3. 身份改用账户名**（`src/sched.cpp`）

`RegisterTaskDefinition` 的 `userId` 参数，文档描述是「用户凭据」，并明确写了「如果任务按 Task Scheduler 1.0 定义，这个参数不要用组名而要用**具体用户名**」——说明它走的是**账户名解析**，不是 SID 解析。实测可用的写法（`schtasks /ru SYSTEM`、各类官方示例）也一律是账户名。

原来的代码传的是 `S-1-5-18`（SID 字符串）。现在改为**优先传账户名**（`SYSTEM`；交互式场景用 `LookupAccountSidW` 把当前用户 SID 翻回 `DOMAIN\User`），SID 作为第 3/5 顺位的备选保留。

> 这一条只是**可疑点**，不是确证的根因——降级链会在真机上自动把答案试出来。

**4. 完整诊断日志**（`src/sched.cpp`）

每次注册都会把尝试过程追加到 **exe 同目录的 `PlanPower_task.log`**（写不进去时退到临时目录）。日志用 UTF-16LE + BOM，记事本可直接打开。内容形如：

## v0.3.0 开机静默启动

### 需求

> 开机启动时不显示软件界面，直接托盘图标。

### 判定依据：一个显式开关，不猜

「这次启动是不是开机自启拉起的」——所有靠推断的写法都不可靠：

| 想过的办法 | 为什么不行 |
|---|---|
| 看父进程是不是 `explorer.exe` | 用户双击也是 explorer 拉起的，分不开 |
| 看启动耗时 | SSD 上跟手动双击没差别，冷热启动差距比这大得多 |
| 看有没有登录脚本 / 会话类型 | 计划任务、组策略、第三方启动器都能拉起程序 |
| 记录「上次退出方式」 | 关机时程序多半被强制结束，写不进状态 |

所以判定依据只有一个：**自启动的 Run 项里有没有 `/tray`**。

```
HKCU\...\Run\PlanPower = "<exe 路径>" /portable /tray
```

手动双击 exe 永远不带这个参数，所以**手动启动永远有界面**。这个区分是传进来的，不是算出来的。

### 三条实现要点

**1. 窗口照建，只是不显示**

「不显示」只影响 `ShowWindow` 这一个动作。托盘图标挂在主窗口上收 `WM_TRAYMSG`，500ms 的计时器也挂在它上面——因为「不显示」就跳过 `TrayAdd` / `SetTimer`，表现会是「托盘里没有图标、任务也不会执行」，而且完全不报错。

```cpp
if (startHidden) {
    ShowWindow(g_hMain, SW_HIDE);
} else {
    ShowWindow(g_hMain, nCmdShow);
    UpdateWindow(g_hMain);
}
TrayAdd(g_hMain);                 // 这两句不在 if 里
SetTimer(g_hMain, IDT_TICK, 500, nullptr);
```

用 `SW_HIDE` 而不是「干脆不调 `ShowWindow`」：显式隐藏会把窗口的可见状态置成确定值，之后 `ShowWindow(SW_SHOW)` 一定生效。依赖 `CreateWindowExW` 的默认隐藏状态，会碰到「第一次 `SW_SHOW` 没反应、要点两次」这类只在某些 shell 版本上出现的怪毛病。

**2. 重复触发时不许弹窗**

单实例分支原来无条件 `ShowWindow(prev, SW_RESTORE)`。开机时如果有两条启动项（比如用户还留着一条旧的手动启动项），第二条会把已经缩在托盘里的窗口硬拉出来——用户刚登录就被一个窗口挡住。

```cpp
if (prev && !trayOnly) { ... }    // 静默启动时不叫醒已有的那一份
```

顺带修了一处：`SW_RESTORE` 对「从未显示过」的窗口不保证能带出来，改成先判 `IsIconic`。

**3. 升级要自动对齐**

v0.2.2 写进注册表的启动项没有 `/tray`，光换 exe 不会让新行为生效——用户得手动把开关关掉再打开一次，而他根本不知道该这么做。

`UI_RepairAutostart()` 在启动时把现值与 `AutostartCommand()` 比对，不一致就重写。两条边界是刻意的：

- **值被删掉了就不复活。** 用户可能在任务管理器的「启动」页里禁用了它。程序自己加回去是最招人烦的行为之一。
- **值指向别的副本就不抢。** 同一台机器上可能放着两支 U 盘，各自都开着自启，抢同一个值名没有意义。

[✓] 开机启动时只显示托盘图标，不弹出主界面      ← 新增

## v0.3.1 开关绑错字段

### 症状

> 除了倒计时，其他每天每周等选项不能点开关暂停任务。

这是 bug，不是设计。而且「只有倒计时能停」本身也不是设计，是**巧合**。

### 根因：两个字段被当成一个用

任务模型里有两个布尔：

| 字段 | 含义 |
|---|---|
| `enabled` | 这条任务**是否启用** —— 语义上的开关 |
| `running` | 这条任务**是否已排进本进程的内存计时器** —— 实现细节 |

开关的显示和点击都绑在 `running` 上。但 `running` 对两类任务并不跟随 `enabled`：

- **每天 / 每周**：`ScheduleTask` 里有「已在计时且未要求重置 → 保持原有进度」的短路，执行完又立刻重排下一次，所以 `running` 只要 `enabled` 就**恒为真**。
- **系统持久任务**：执行者是 Windows，本进程根本不排期，`ScheduleTask` 进门就 `running = false`，所以它**恒为假**。

于是点击时按 `!running` 翻转：

```
running == true（每天/每周） → 走「关」分支
                              → 只清 running，enabled 仍是 true
                              → UI_RefreshAll 重新排期
                              → running 又变回 true
                              → 开关弹回原位，看起来「点不动」
```

倒计时之所以能停，是因为那个分支里多了一行 `if (kind == Countdown) enabled = false` —— 它把真正该翻的字段顺手翻了。**一个特例让错误的主逻辑看起来是对的**，这也是它一直没被发现的原因。

同一个根因还有第二个症状，之前没人报：**系统持久任务的开关永远显示为关**（`running` 恒假），哪怕它正在按时关机。点一下也没反应。

### 修法

引入一个显式的语义函数，把「生效中」这件事说清楚：

```cpp
static bool TaskActive(const PowerTask& t) {
    if (!t.enabled) return false;
    return t.persistent ? true : t.running;
}
```

- 开关的**显示**改为 `t->enabled`，点击改为 `turnOn = !t->enabled`；停用时清 `running`，启用时 `ScheduleTask(*t, true)` 强制重算（丢掉停用前的旧 `dueTick`）。
- 开关的**绘制**去掉了原来的「是否可交互」参数：停用的任务必须能点回来，画成禁用态会让人以为点不了。
- 状态点、「运行中」标签、「运行中 / 已停用」两个筛选、以及标签上的计数，全部改走 `TaskActive` / `enabled`。**筛选和计数必须与列表同源**，否则数字和条目会对不上。
- 点击处理里那个 `if (kind == Countdown) enabled = false` 的特例删掉了 —— 特例消失，才说明主逻辑是对的。

### 一个需要说清楚的语义

停用再启用**不会接着原来的进度**：每天/每周按日历重算下一次，倒计时按 `delaySeconds` 从当前时刻重新开始。

这是刻意的。「停用」是「不再自动执行」，不是「暂停 / 继续」；后者的语义要求保存剩余时间，而剩余时间是运行期状态，不该写进配置文件。如果你要的是暂停后接着走，这是另一个需求。

### 验证

`check_layout.py` 新增 E21 组 **18 项**断言，锁住这几件事：`TaskActive` 必须区分系统任务、筛选与计数必须同源、开关必须绑 `enabled`、停用必须清 `running`、启用必须强制重算、点击处理里不得再出现倒计时特例。

反向验证 **12/12 命中**：开关点击改回 `!running`、开关绑回 `running`、`TaskActive` 不区分系统任务、`TaskActive` 不看 `enabled`、「运行中」筛选改回 `running`、「已停用」筛选改回旧式、`CountFilter` 改回 `running`、`DrawToggle` 加回可交互参数、停用不清 `running`、启用不强制重算、状态点改回 `running`、恢复倒计时特例。

## v0.3.2 静默失效的口子与改进清单

这一轮不是按功能列表加的，而是回头把代码当「别人的代码」读了一遍，专门找**不报错、但结果与用户以为的相反**的地方。

### 已修：三个静默失效的口子

**① 点「退出」= 悄悄取消所有内存计时任务**

托盘菜单的「退出」原来是 `DestroyWindow(hwnd)`，一句确认都没有。内存计时器活在进程里，进程一没，那个「30 分钟后关机」就永远不会发生——而用户以为自己只是关掉了界面。**这是整个程序里唯一一处「操作成功、结果却相反」的地方。**

现在退出前会列出正在计时的任务和各自剩余时间，默认按钮是「取消」：

```
以下任务正在计时，退出程序后不会执行：

  · 30 分钟后关机（00:27:14 后）

要让它们在关掉界面后仍然执行，请改用「系统持久任务」。
```

没有任务在计时时不弹——确认框只在真的会丢东西时出现，否则就是噪音。

**② 统计把停用的任务算成「正在跑」**

标题副标题、状态栏、托盘提示三处都在数 `persistent` 字段，而停用的系统任务照样占着这个字段。于是「3 个系统任务由 Windows 调度」里可能有两个是停用的。现在只数 `enabled` 的，状态栏的「N 个运行中」也改成「N 个启用」——**用词跟着语义走，比换个数字更有效**。

**③ 连点两次「30 分钟后关机」会留下两条任务**

托盘快捷菜单每点一次就 `AddTask` 一条。两条同名任务到点各执行一次，第一次关机后第二次的 `shutdown.exe` 还会再跑一遍。现在会先找「同样时长 + 关机 + 内存计时 + 启用中」的已有任务，命中就**重置它的计时**——连点两次的直觉是「从现在重新数 30 分钟」，不是「排队关两次」。

顺带清掉一个死字段：`PowerTask::firedTick` 声明时注释写着「上次执行时刻，用于防止重复触发」，但全项目**一次都没读写过**。留着比没有更危险——下一个读代码的人会以为防重复触发的机制已经存在。

### 改进清单（按「值不值得做」排序，不是按工作量）

#### 第一梯队：影响「这件事能不能做到」

**1. 「指定时刻」其实不能指定日期**

`TriggerKind::OnceAt` 只有 `hour` / `minute` 两个字段，`ComputeDueTick` 的算法是「今天这个点，过了就顺延到明天」。所以它实际是「下一个到达这个时刻的时候」，**用户无法表达「10 月 25 日早上 8 点关机」**——只能靠「每周 + 只勾周五」凑，而且周五之后的那次还得手动删。

这是目前最明显的功能缺口，也是唯一一个「用户想做的事根本说不出来」的地方。代价：`PowerTask` 加一个日期字段、INI 序列化、`ComputeDueTick` 加分支、编辑窗加日期选择（Win32 只有 `DATETIMEPICK_CLASS`，会引入 `comctl32` 的 `ICC_DATE_CLASSES`，已经在链接的库里）。

**2. 睡眠期间的内存倒计时会不会停摆（待真机确认）**

内存计时用的是 `GetTickCount64`。如果它在 S3 睡眠期间不累加（按 Windows 的常见行为推测是这样），那么「30 分钟后关机」在合盖睡 1 小时再打开后，会显示还剩 30 分钟——**合盖的时间不算数**。

系统持久任务不受影响（执行者是 Windows，还有 `WakeToRun`）。这一条我**无法在 macOS 上验证**，所以没有改。如果真机确认成立，修法是给任务额外记一个墙钟截止时刻，`UI_Tick` 以墙钟为准——但要处理用户手动改系统时间的情况。

**3. 内存任务错过执行时间没有任何补偿**

程序没运行的那段时间里到点的任务，就永远错过了。系统任务有 `StartWhenAvailable=true` 会补跑，但那也有反效果：电脑关一周再开机，每天 23:00 的关机任务可能一开机就执行。

#### 第二梯队：每天用都会碰到

| 项 | 现状 | 建议 |
|---|---|---|
| 快捷关机时长 | 写死 30 / 60 / 120 分钟 | 设置里可配，或加「自定义…」 |
| 日志清理 | 按天分文件，永不删除 | 保留最近 N 个月；或在设置里显示占用并给「清空」 |
| 全部暂停 | 只能一条条点开关 | 「暂停全部 / 恢复全部」，托盘菜单里也能用 |
| 执行历史 | 只有 `logs/*.log` 文本 | 界面上一个「最近执行」列表，读日志文件即可 |
| 键盘操作 | 主窗口列表是自绘的，没有焦点 | ↑↓ 选任务、空格切换开关、Delete 删除 |
| 任务重名 | 允许，界面上分不清 | 保存时提示「已有同名任务」 |

> 这张表是 v0.3.2 当时的现状。**第一梯队与第二梯队六项已在 v0.4.0 全部做完**（见 [v0.4.0 第二梯队](#v040-第二梯队)），下面只剩第三梯队。

#### 第三梯队：工程卫生

- **系统任务漂移检测**：用户在 `taskschd.msc` 里手动改了或删了某条任务，程序不知道，界面仍显示「已注册」。启动时用现有的只读枚举比对一次，不一致就在任务行上标「状态异常」。
- **配置文件损坏没有退路**：INI 解析失败时任务会静默丢失。可以在加载前留一份 `.bak`，解析出 0 条而文件非空时提示恢复。
- **没有导入/导出**：换 U 盘或换机器要手动拷 `PlanPower.ini`。加一对按钮即可，但要注意任务 ID 冲突。
- **`SetProcessDPIAware()` 不是 per-monitor v2**：多显示器不同缩放时，窗口拖到另一块屏会模糊。改 `SetProcessDpiAwarenessContext` 要连带处理 `WM_DPICHANGED` 重排，代价不小。

#### 明确不建议做

- **深色模式**：全部自绘，每个颜色常量都要再来一套，收益只对少数人有。
- **多语言**：文案散在自绘代码和 XML 里，抽取成本远高于收益。
- **云同步 / 账号体系**：和「单文件、零依赖、U 盘即插即用」是根本冲突的定位。

## v0.4.1 日志乱码

**症状：** 打开 `logs\2026-10.log`，中文任务名全成乱码。

**根因：** 日志按 UTF-16LE 写盘，但**没有写 BOM**。这串字节本身是合法的，问题在于「怎么被解读」——记事本只能靠猜，猜错就是整篇乱码；VS Code / Notepad++ 干脆按 UTF-8 或 GBK 解，中文全成问号。

有意思的是同一份代码里，`sched.cpp` 的诊断日志（`PlanPower_task.log`）一直是带 BOM 的，主日志却漏了。两处各写一套，就差这一步。

**修法：**

1. `LogLine` 改走 `TextToUtf16Le`（和诊断日志同一个函数），新建文件时写 BOM，追加时按文件大小摘掉——否则 BOM 会落在文本中间，被当成一个 U+FEFF 显示成方块。
2. **老文件补 BOM。** 只保证新文件正确的话，用户得等到下个月才能看到能读的内容。所以升级后**第一次启动**就扫一遍 `logs\*.log`，把无 BOM 的就地补上。用原子写而不是「在开头插 2 字节」：后者要把整段内容后移，中途失败就把日志写坏了——为了修显示问题弄丢内容说不过去。

   （挂在「第一次写日志」上不够：用户可能好几天不触发任何任务，那期间老日志一直是乱码的，他会以为没修好。所以单独抽成 `LogMaintenance()`，`UI_Create` 里主动调一次。）
3. 读取端跳过 BOM，且**两种格式都认**。升级不该要求用户清空 `logs`。

**顺带修掉一个假失败。** `tools/xmltest.cpp` 假设 `/tmp/pp_xml` 已经存在。`/tmp` 会被系统按天清理，目录一没，十几个用例的写文件全部失败，控制台上是一排「失败」——看起来像代码坏了，其实只是环境被清了。改成自己 `mkdir`。

这类假失败比真失败更费时间：它把注意力引到完全无关的地方。

### 为什么这类缺陷静态检查抓不到

编译不报错、程序功能正常、断言全过——只有用户真的双击那个文件才看得见。和上一版「exe 属性里的中文描述乱码」是同一类。

所以 E25 不查「有没有写日志」，而查到编码这一层：`LogLine` 必须走 `TextToUtf16Le`、追加必须按文件大小摘 BOM、`LogMaintenance` 必须同时调清理和补 BOM、补 BOM 必须原子写、读取端必须跳过 BOM、两处日志必须同一种编码。**反向验证 9/9 命中。**

## v0.4.0 第二梯队

v0.3.2 末尾列了一份改进清单。这一版把**第一梯队（指定时刻加日期）**和**第二梯队六项**全部做完。

### 1. 「指定时刻」可以指定具体日期

原来 `OnceAt` 只有小时和分钟，语义是「今天这个点，过了就顺延到明天」。要排「后天下午三点」只能靠倒计时算到那个时刻，或者等明天再建。

现在多了 `year / month / day` 三个字段，编辑窗在「指定时刻」下多出一行日期输入。

**难点是兼容。** 老配置里没有这三个键。如果直接按「日期为 0 = 无效」处理，升级后所有历史任务都会变成「日期不合法」。所以定成双语义：

| `year` | 含义 | 行为 |
|---|---|---|
| `0` | 旧配置（v0.3.2 及以前写的） | 沿用「今天这个点，过了顺延到明天」 |
| `> 0` | 已具体化日期 | 「某个确切时刻执行一次」，**错过就是错过** |

在编辑窗里保存过一次，日期就会被具体化。这不是偷偷改变行为：用户既然打开了编辑窗、看见了日期输入框，就说明他要的是确切日期。

配套的两道拦截：

- **保存时校验日期真实性**（`ppdate::ValidDate`），2 月 30 号当场拒绝；
- **保存时拦「已过去」**（`CompareFileTime`）。存一个过去的时刻没有任何意义，界面只会写「已过期」，不如当场说清楚。

闰年判断只有一份实现，在 `dateutil.h` 这个纯头文件里。`core.cpp`（Win32 层）和 `sched_xml.cpp`（纯逻辑模块，宿主机单独编译、不链接 core.cpp）都引用它——两边各写一套迟早会漂移，而漂移的表现是「编辑窗放行、写 XML 时拒绝」。

### 2. 快捷关机时长可配

托盘菜单原来写死 30 / 60 / 120。现在读 `Quick1 / Quick2 / Quick3`，设置里填「30,60,120」这样一个输入框。读出来夹到 `[1, 1440]`——INI 是纯文本，用户手改成 `99999` 之后菜单里出现「99999 分钟后关机」比不允许改更糟。

### 3. 日志按月清理

原来日志永不删除，一年下来 12 个文件。现在保留最近 N 个月（默认 6，可配 0–120，0 表示不清理）。

**这是整个程序里唯一会删除用户文件的地方**，所以边界写死：

- 文件名必须正好 11 字符、第 5 位是 `-`、其余全是数字；
- 年 2000–9999、月 1–12；
- 只删本程序按 `%04d-%02d.log` 生成的那种名字。

判断抽成 `IsLogFileName()` 一份，**清理和读取共用**。两边各写一套的话迟早会漂移，而漂移的方向恰好是「清理删得比读取宽」——把用户自己放进 `logs` 目录的东西删掉。宁可漏删一个不认识的文件。

清理每次运行只做一次（`static bool purged`），不是每写一行都扫目录。

### 4. 全部暂停 / 全部启用

托盘菜单两项，主界面不用逐条点开关。

系统持久任务要写任务计划程序，需要提权。**整批合成一次 UAC**：逐条走会弹 N 次，而用户点的是一个「全部」按钮。做法是在 `sched` 层加一个 `SchedOp::SetAllEnabled` 操作，命令行 `/sched-set-all <配置> <1|0>`，提权进程里一次改完。

名单来自**归属表**（`g_store.HostTaskNames()`），不按文件夹扫。按文件夹扫会把别的 PlanPower 副本注册的任务一起改掉。

这一条有个容易漏的地方：`SchedRunElevated` 在函数里出现 1 次还不够，**那次调用必须直接躺在 `if (anySys)` 块里**。嵌进 `for` 就是逐条提权，而调用次数仍然是 1，光数次数看不出来。断言因此查缩进。

### 5. 执行历史窗

主界面右上角多了一个时钟图标，托盘菜单也有「执行历史…」。

数据来源就是 `logs\YYYY-MM.log`，不另建一份历史记录。**同一个事实只能有一份记录**——多一份就可能和日志对不上，而用户看到对不上的时候不知道该信哪个。

窗口本身很薄：一个只读多行编辑框（滚动、选中、Ctrl+C 全是系统给的），加「打开日志文件夹」和「关闭」。读最近 300 条，跨月自动往前翻，正序显示，光标落在末尾。

### 6. 列表键盘操作

↑↓ 选行、Home / End 跳首尾、空格切换开关、回车编辑、Delete 删除。

关键设计：**鼠标和键盘共用同一个 `ActivateRowElem(hwnd, row, elem)`**。两份实现迟早会分叉，而分叉的表现是「键盘删任务没删掉系统任务」——一个只有用键盘的人才会遇到的 bug。

另外 `g_selRow`（键盘选中）与 `g_hoverRow`（鼠标悬停）是分开的两个变量。合成一个的话，鼠标一移开键盘选中就丢了。

### 7. 重名提示

保存时如果已有同名任务，提示一次，但**不禁止**。重名是个合法需求（「周一 8 点关机」和「周五 8 点关机」可以同名），程序没有立场替用户决定名字。

### 顺带修掉的一个隐患：`LogLine` 的短文案会被优化掉

这一版加了 `LogLine(L"全部暂停")` 这类 4 个字的日志文案。构建时 `check_strings.py` 报「二进制里找不到这两条」——一开始以为是 `-O2` 那个常量合并的老毛病，最小复现之后发现是另一回事：

`LogLine` 的参数是 `const std::wstring&`，4 个 `wchar_t` 正好塞进 libc++ 的短串缓冲区（SSO），clang 于是把它们直接编成两条 `movl` 立即数写进去，**rodata 里那份字面量成了死数据被删掉**。功能完全正常，但文案自检靠「在 exe 里找得到这条串的 UTF-16 字节」来判断有没有被拼坏——串不在 rodata 里，这道防线就看不见它了。

修法是给 `LogLine` 加一个 `const wchar_t*` 重载（原语），`wstring` 版转发过去。字面量以指针形式传给另一个翻译单元的函数，编译器必须把它留在 rodata。顺带每行日志少一次临时 `std::wstring` 构造。

**教训不是「加个重载」，是「一个检查手段有它看不见的地方，而看不见的地方恰好和它要防的缺陷长得一样」。**

### 顺带修掉的两处：exe 属性里的版本号与中文描述

这两个都只在 Windows 上「右键 → 属性 → 详细信息」才看得见，构建不会报任何错，所以一直没人发现。

**版本号停在 0.3.2.0。** `planpower.rc` 的 `FILEVERSION` / `PRODUCTVERSION` 与两个字符串字段写死在资源里，项目到了 v0.4.0 却没跟着改——上传的 exe 属性里显示的仍是旧版本。现在 `check_layout.py` 的 E24 会拿 `.rc` 的版本号去对 README 里「当前为 vX.Y.Z」那句话，不一致就让构建失败。

**文件描述显示成乱码。** `.rc` 里的 `FileDescription` 是中文，而 `windres` / `rc.exe` 默认不按 UTF-8 读，会把 UTF-8 字节逐个当成 Latin-1 转成宽字符，属性里就变成：

## 已知边界（v0.4.1 原型）

1. **运行期行为未在 Windows 上实测。** 本机为 macOS，只做了编译期、PE 结构、配置往返、任务 XML 与界面布局的离线验证。UAC 提权、任务计划程序的实际注册与执行、托盘气泡是否弹出，都需要在真机上验证。
2. **`0x80041318` 的确切病灶尚未定位。** v0.2.2 的降级链能保证注册成功（五种写法总有一种会被接受），诊断日志会记下是哪一种，但**「服务端到底在挑剔哪个取值」还没有从根上确认**。真机跑一次后看 `PlanPower_task.log` 里 `[成功]` 那一行的标签就能知道。如果最终发现是某个具体元素，应把它从两套定义里都去掉，并把降级链收缩回一条。
3. **降级链的代价是「首次注册最多 5 次 COM 往返」。** 都发生在同一个提权进程内，不重复弹 UAC；失败的尝试在任务计划程序里不留下任何痕迹（`RegisterTaskDefinition` 是原子的）。成功后会记住吗？——**不会**，每次注册都从第 1 种写法重新试。这是刻意的：缓存「哪种写法可用」会引入一份需要失效判断的状态，而这条链的开销（毫秒级）远小于它的维护成本。
4. **托盘气泡不是保证送达的。** 开机静默启动时程序会发一次气泡提示，但 Windows 允许用户关闭通知、专注助手也会吞掉它。**托盘图标本身才是唯一可靠的信号**，气泡只是补一句解释。没有收到气泡不代表程序没起来。
5. **「只显示托盘图标」只对自启动那一次生效。** 手动双击 exe 永远会打开主界面——这是刻意的，靠 `/tray` 显式传递而不是猜启动来源。想连手动启动也静默，当前没有开关（也不建议加：双击图标却什么都没出现，是最容易被当成崩溃的体验）。
6. **睡眠可能变休眠。** 若系统已启用休眠，`SetSuspendState(FALSE,...)` 在部分机型上会执行休眠而非睡眠。这是 Windows 的已知行为，可用 `powercfg /h off` 关闭休眠来规避。
7. **系统任务的动作受限。** 任务计划程序只能「启动一个 exe」，所以持久任务由 `shutdown.exe` / `rundll32.exe` 执行，不是 PlanPower。收尾动作、看门狗这类需要本程序在场的功能无法做成系统任务。
8. **「清理本机系统任务」是按文件夹清的。** 它不区分介质，会把其他 PlanPower 副本（比如另一支 U 盘）在这台电脑上注册的任务一并删掉。这是刻意的——归属表可能丢失，而 `\PlanPower` 这个约定不会。
9. **系统任务不显示实时倒计时。** 执行者是 Windows，本程序不参与计时，所以任务行只给出按规则推算的「下次执行」时刻。倒计时/指定时刻这类一次性任务显示为「一次性 · 已交给系统」——按「当前时间 + 延迟」重算只会显示成永远差 30 分钟。
10. **无深色模式。** 当前只有浅色主题。
11. **x86 版依赖 UCRT。** 见上文「关于 `api-ms-win-crt-*` 的说明」；要向下兼容 Windows 7/8.1 请用 `build_msvc.bat`。
12. **停用再启用不接着原来的进度。** 每天/每周按日历重算下一次，倒计时按设定的延迟从当前时刻重新开始。「停用」是「不再自动执行」，不是「暂停 / 继续」——后者要求保存剩余时间，而剩余时间是运行期状态，不该进配置文件。
13. **指定时刻一旦在编辑窗里保存过，日期就被具体化。** 之后按「某个确切时刻执行一次」处理：错过就是错过，不会再顺延到明天。这是刻意的——用户既然看见并确认了日期输入框，要的就是确切日期。旧配置（没这三个字段）保持原来的顺延语义。
14. **执行历史只显示最近 300 条，且依赖日志开关。** 关掉「记录执行日志」之后历史会一直是空的。另外它是只读的：删日志要用「打开日志文件夹」手动删，程序不提供「清空历史」按钮——那等于给这个程序再加一个删文件的动作，而删除是这个程序里最危险的操作。
